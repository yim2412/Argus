## 프로그램별 누적 실행 시간 (2026-08-12)

사용자 요청은 "어떤 프로그램을 얼마나 썼는지 **계속 누적되게** 보고 싶다"였다.
별도 프로그램이 아니라 Argus 에 넣었다 — 새 수집기가 필요 없고(`procsource` 가 356개를
33.3ms 에 가져온다) 상주가 둘이 되면 설계 규칙 1 위반이다.

**순진한 두 경로가 둘 다 틀린 값을 준다** (실측, 관측 383시간 기준):

```
                A: process_5m 버킷    B: events 수명 합계
chrome                237.8h              1,073.0h
discord               238.8h                125.4h
steam                 238.6h                 17.9h
```

A 는 **포화한다** — 5분 버킷에 한 번 보이면 5분을 다 세므로 오래 켜 두는 것은 전부
관측 전체(238.8h)로 붙는다. 실행 시간이 아니라 *존재 여부*다. B 는 **이중계산한다** —
chrome 프로세스 4,443개의 수명 합이라 "프로세스-시간"이지 "chrome 이 켜져 있던
시간"이 아니다. 올바른 계산은 **이름 단위 구간 합집합 + 관측 세션 클램프**이고,
시제품 검증값(overwatch 5.3h · LoL 29.9h)을 구현이 그대로 재현했다(5.35h · 29.91h).

### 이름이냐 실행 경로냐 — 이름으로 정한 근거

DB 에 `exe` 가 이미 있어 경로 기준을 그대로 시뮬레이션할 수 있었다. 이름 424종 중
경로가 둘 이상인 것은 67종(16.6%)인데, 그 정체가 판단을 갈랐다.

```
discord    64  ...\Discord\app-1.0.9251\Discord.exe
           25  ...\Discord\app-1.0.9250\Discord.exe
           11  ...\Discord\app-1.0.9249\Discord.exe
```

**자동 업데이트마다 경로가 바뀐다.** 16일에 버전 폴더 3개이므로 경로로 나누면 "얼마나
썼나"가 1년 뒤 수십 줄로 조각난다 — 누적을 보겠다는 요청과 정반대다. 반대로 경로
분리가 도움이 되는 사례는 `python`(uv · `.venv` · pythoncore) 하나뿐인데 **그건 개발
환경에서만 생긴다.** 배포된 `argus.exe` 로 도는 PC 에는 그 줄이 아예 없다. 이득은
개발자 1명, 손해는 전원이다. 게다가 경로는 민감 정보(규칙 5)이고, 컬럼 추가는 나중에
쉽지만 제거는 남의 PC 의 DB 를 고치는 일이 된다.

`python`·`node` 뭉침이 나중에 거슬리면 **그때 config 에 "경로까지 나눌 이름 목록"을**
두는 것이 맞다. 지금 넣으면 쓰지 않을 복잡도다.

### 구현에서 드러난 것

- **`exit` 이벤트에는 이름이 없다.** 수집기가 PID 만 남긴다(이미 죽은 프로세스의
  이름은 물어볼 데가 없다). `start` 로 연 PID 를 기억해 맞춰야 한다.
- **`exit` 이 없는 구간을 열어 두면 값이 샌다.** 처음엔 남은 구간을 처리 범위 끝까지
  늘렸는데, 큐 드롭으로 `exit` 하나가 사라지면 짧게 살다 죽은 프로세스가 며칠이 된다.
  **모든 구간을 그 구간이 시작된 세션 안에서 끝내도록** 고친 뒤 실측이 크게 바뀌었다
  (`searchprotocolhost` 241h → 155h, `conhost` 235h → 209h). 잘라도 잃는 것은 없다 —
  세션이 끝나도 살아 있었다면 다음 세션의 첫 스냅샷이 `start` 를 다시 낸다.
- **기동 직후의 `start` 폭주는 실행 횟수가 아니다.** 수집기는 첫 스냅샷에서 이미 떠
  있던 프로세스 전부를 신규로 본다(`_known` 이 비어 있다). 세면 부팅마다 크롬을
  200번 실행한 것이 된다.
- **배경 서비스가 상위를 차지하는 것은 버그가 아니다**(svchost 는 늘 떠 있다).
  화면에서 그렇게 말해 주지 않으면 값이 틀린 것처럼 보여서, 페이지에 한 줄 적었다.

### 남겨 둔 것

"켜져 있던 시간"과 "실제로 쓰던 시간"은 다르다. 후자는 포어그라운드 비율
(`process_5m.foreground_ratio`)로 만들 수 있지만, 요청은 실행 시간이었고 데이터
계층이 달라 이번에 넣지 않았다. 필요해지면 같은 테이블에 컬럼 하나를 더한다.

## 창 사용성 개편 (2026-08-12 오후)

사용자 요청("직관적이고 간편하게, 한눈에 들어오게")으로 시작했다. 측정부터 하니
**"빽빽하다"와 "HD 로 안 열린다"가 같은 원인 하나**였다.

```
창 실제 크기  1280x1255   ← resize(1280, 720) 이 무시되고 있었다
자기 상태 페이지 minHint 1179px  ← 이 하나가 창 전체의 하한을 정했다
```

`QStackedWidget` 은 담긴 페이지 전부의 최소 높이 중 **최댓값**을 자기 하한으로
삼는다. 스크롤 영역이 하나도 없어 가장 빽빽한 페이지가 나머지 여섯을 끌고 다녔다.
**예외도 경고도 없이 크기 요청만 무시**되므로 `--seconds` 스모크는 그 상태에서도
전부 정상이었다.

한 것: 페이지를 `QScrollArea` 에 담고(`8a36990`), 자주 안 보는 것을 접고
(`4035d2e`, 자기 상태 1179→674 · 타임라인 824→632), 맨 위에 "지금 괜찮은가" 한 줄을
놓고(`d2e97d4`), 병목 자원의 타일만 강조하고(`c08eefc`), 탭을 보기/진단으로 나누고
(`5feb43c`), 창 크기를 닫을 때 기억하게 했다(`006aa78`).

**상태 한 줄에서 지킨 것 둘.**

1. **수집이 멈췄는지를 사건보다 먼저 본다.** 멈추면 사건도 안 생기므로 "정상"과
   "죽음"이 똑같이 조용해 보인다. 그 상태로 초록불을 켜면 사용자는 모니터가 죽은
   것을 모른 채 안심한다(설계 규칙 4).
2. **문장을 다시 만들지 않는다.** `incidents.title` 이 이미 "디스크 병목 —
   chrome 68%" 형태다. 두 곳에서 만들면 두 곳이 갈린다.

**타일 색은 문턱을 새로 만들지 않았다.** 원래 계획은 "정상/주의/위험 문턱"이었는데,
그러면 (1) 하드웨어마다 틀리고(디스크 응답 50ms 는 HDD 사용자에겐 오탐 — 규칙 2),
(2) 탐지기와 별개의 두 번째 판정이 생겨 맨 윗줄과 갈린다. `decide/severity` 가 이미
machine 상대값으로 매긴 판정을 그대로 옮긴다 — **UI 에 임계값이 0개**다.

## 프로그램이 무엇인지 · 내가 쓴 것만 (2026-08-12 오후)

"svchost 238시간"은 정보가 아니다. 두 단계로 고쳤다.

**1. 이름 옆에 사람 말 설명**(`f23d88a`). 출처는 exe 의 버전 리소스(탐색기 속성
창의 "파일 설명")다. `ctypes` 로 `version.dll` 을 부르므로 새 의존성이 없고 한글
Windows 에서는 한글이 나온다. 경로는 `process_events.exe` 에 이미 있었다(427종 중
405종) — 새 수집기가 필요 없었다.

**언어를 파일에서 읽는다.** 흔한 구현처럼 `040904b0`(미국 영어)을 박으면 한글
Windows 의 시스템 파일에서 전부 빈손이 되는데, **예외가 아니라 빈 설명**이라 본인
PC 에서는 안 보인다 — PDH 카운터명과 같은 로케일 함정이다.

실측: 405종 3.6초 · 개당 8.8ms · 성공 289/405(71%). 못 읽는 29%는 파일이 이미
지워졌거나 버전 리소스가 없는 exe 다.

**2. 배경 서비스 걸러내기**(`8bf77a6` · `9def309`). 포어그라운드 이력으로 가른다 —
창을 띄워 앞에 놓인 적이 있으면 사람이 쓰는 프로그램이다.

```
200종  →  74종(포어그라운드)  →  61종(usage.exclude 적용)
```

**경로나 회사명으로는 안 갈린다.** `crashpad_handler`(사용자 폴더)·`node`·
`saclient`(Program Files)가 전부 통과하고, Microsoft 를 빼면 탐색기·작업관리자까지
사라진다.

**한 번 참이면 계속 참으로 저장한다.** 포어그라운드 원본(`process_5m`)은 이틀이
지나면 웜으로 옮겨가므로, 매번 다시 판정하면 사흘 전에 한 게임이 목록에서 빠진다.

개발 도구·셸 호스트는 `usage.exclude`(YAML)로 더 뺀다. 사람마다 경계가 다르므로
코드가 아니라 설정이다 — 개발자에게 터미널은 도구지 콘텐츠가 아니고 누군가에게는
그 반대다. `applicationframehost` 는 UWP 앱의 창틀인데 실측 155시간으로 3위였다.

### 테스트 격리 사고 둘 (같은 뿌리)

- fixture 가 `tmp_path` DB 만 쓰고 `warm_dir()` 을 그대로 둬서 **테스트가 실제 웜
  파티션을 읽었다.** 이 PC 의 게임 목록이 단언 실패 메시지에 튀어나왔다.
- 그걸 고치며 `ARGUS_DATA_DIR` 을 tmp 로 돌렸더니, 이번엔 fixture 가 만드는
  `t.db` 와 조회 계층이 여는 `argus.db` 가 **서로 다른 DB** 가 됐다. 조회가 늘
  빈손이었고 실패가 "필터가 안 먹는다"처럼 보였다.

**교훈: 데이터 폴더를 격리할 때는 폴더 경로와 파일명을 함께 맞춘다.** 하나만
바꾸면 실데이터를 보거나 아무것도 안 보거나 둘 중 하나다.

## 웜 내보내기: 스트리밍 + 프로세스 분리 (2026-08-12)

아래 "RSS 예산 초과는 누수가 아니었다"의 후속이다. 그 판정이 원인을 두 개로 나눠
적어 뒀는데(**임포트 366MB** 와 **내보내기가 하루치를 올리는 것**), 계획서에는
후자만 남아 있었다. 둘 다 처리했고, **비중이 반대였다.**

### 계획서의 진단이 절반 틀렸다

`PLAN.md` 는 "하루치 `process_5m` 을 통째로 올려서 rss 가 300MB 를 넘는다"고 적어
두었다. 실제 하루치를 세어 보니 그 설명이 성립하지 않는다:

```
하루치 실제 규모   metrics 1,160행 · process 12,451행   (파티션 최대값)
피크 시각의 로그   06:43 급증 구간에 웜 내보내기 없음 — 롤업(buckets:1)만 돌았다
그 구간 private    535.5MB 로 미동 없음 — RSS 만 55 -> 745MB 로 오르내렸다
```

**private 이 움직이지 않았다는 것이 답이다.** 745MB 는 새 할당이 아니라 *이미
커밋돼 있던* private 이 워킹셋에 들어온 순간이었다. 그 private 을 만든 것은
`import pyarrow` 다:

```
import duckdb          private + 10.1MB   pyarrow 안 끌어옴
Parquet 조회 전체        private   36.4MB   pyarrow 안 끌어옴
import pyarrow         private +366.4MB
```

지문 빌드·발열 드리프트도 의심해 직접 쟀지만 각각 96MB·51MB 로 끝났다(둘 다 6시간
주기인데 04:24 기동 세션에서 06:43 전에 돌 차례도 아니었다).

### 한 것

1. **스트리밍**(`8a2da3a`) — `pq.ParquetWriter` 로 5만 행씩, 읽기는 별도 읽기전용
   커넥션으로. `db._lock` 보유가 0이 되고 파이썬 힙 피크가 25.2→4.4MB.
2. **프로세스 분리**(`1b2f1e7`) — `argus --export-warm` 을 자식으로 부른다. 자식이
   죽으면 366MB 도 사라진다. **읽기(duckdb)는 상주에 남겼다** — 지문·발열이 웜을
   읽어야 하고 그 경로는 pyarrow 를 안 쓴다.

### 덤으로 잡은 것 — 옛 구현의 `null` 타입 파일

두 구현을 같은 데이터로 나란히 돌려 비교하다 나왔다. 옛 코드는 pyarrow 에 타입
추론을 맡겼는데, **그날 전부 NULL 인 컬럼이 `null` 타입으로 저장된다.** 07-27 을
재내보내니 `gpu_clock_sm_mean` 이 `null` 로 나왔고 다른 날 파일들은 `double`
이었다. 데이터가 드문 날에만 나므로 평소에는 아무 신호가 없다. 새 코드는
`PRAGMA table_info` 로 스키마를 명시한다.

### 사고 — 모킹한 테스트 4개가 통과한 채로 자식이 안 돌았다

프로세스 분리를 커밋하고 상주를 재시작하니 매시간 이 로그가 났다:

```
WARN 웜 내보내기 자식이 실패했다 {'returncode': 1, ... ModuleNotFoundError: psutil}
```

상주는 base `pythonw.exe` 로 돌고 venv 경로를 `site.addsitedir()` 로 세운다
(`tools/soak_entry.py` — venv 트램폴린이 콘솔 창을 띄우기 때문이다). 자식은 그
경로를 물려받지 못한다. **그 파일 첫머리가 경고해 둔 함정에 그대로 빠졌다.**

**테스트 4개가 전부 통과한 상태였다** — `subprocess.run` 을 갈아 끼웠으니 자식이
실제로 뜨는지는 아무도 보지 않았다. 모킹은 "무엇을 호출했는가"를 재고 "그것이
되는가"는 재지 않는다. 실제로 띄우는 테스트를 붙였고, 프로젝트 밖 `cwd` 에서 돌려
"우연히 되는" 경우도 배제한다. 그리고 상주와 같은 인터프리터(base python)로 직접
확인했다 — venv 파이썬으로 도는 pytest 로는 이 조건이 재현되지 않는다.

고침은 부모의 `sys.path` 를 `PYTHONPATH` 로 물려주는 것이다. 어떤 기동 방식이든
부모가 이미 세워 둔 경로를 따라온다.

### 결과 (재시작 후 실측)

```
private   535MB -> 208MB      스레드  46~47 -> 41
```

예산 300MB 아래로 들어왔다. `import pyarrow` 가 상주에서 사라진 값이다.

### 사고 — 검증이 실DB 를 오염시켰다

검증 스크립트가 `warm_dir()` 만 임시 경로로 갈아 끼웠는데, `export_date()` 는

**관측 장치는 더 붙일 것이 없었다.** `private_mb`·`peak_wset_mb`·`page_faults`·스레드·
핸들·큐·드롭·스로틀이 이미 `self_telemetry` 에 들어가고, 창이 `_private_growth()` 로

경사로 보이고, 그러면 없는 누수를 쫓게 된다.

남은 개선(웜 내보내기 스트리밍)은 `PLAN.md` §8 에 있다.

**전체 객체 수가 오히려 줄었다.** CPython 은 원자값만 든 컨테이너를 untrack 하고
`str`·`bytes`·`int` 는 애초에 추적하지 않는다. 문자열만 든 dict 5만 개로 다시 재니
**객체 수 +2 · 원소 수 +50,014** 였다.

개수만 세는 계측이었으면 **캐시가 자라는 것을 통째로 못 봤을 것이다.** 예외가 아니라
"값이 안 움직인다"로 나타나는 종류라 실운용에서는 몇 주 뒤에나 알았을 것이다.

그리고 테스트가 그 다음 부정확함까지 잡았다 — 원소 수는 untracked 객체 *자신* 을
세지 않는다. 그것들은 `gc.get_objects()` 에 나오지 않아 `len()` 을 물을 대상조차
없다. 세는 것은 **그것을 담은 tracked 컨테이너가 커졌다**는 간접 신호다. 최상위
컨테이너 자신이 untracked 면 못 보고, 거기까지 가면 `tracemalloc` 이 필요하다.

## 풍선 알림을 무음으로 (2026-08-13)

알림이 뜰 때마다 Windows 기본 알림음이 났다. **소리는 알림의 부가가 아니라 알림 자체의
비용을 바꾼다** — 상주의 알림은 사용자가 부른 것이 아니라 끼어드는 것이고, 오탐 3번이면
사용자는 알림을 끈다(탐지 규칙 1). 그래서 기본을 무음으로 두고 원하면 켜게 했다.

`Shell_NotifyIcon` 의 `dwInfoFlags` 에 `NIIF_NOSOUND`(0x10)를 **OR** 한다. 덮어쓰면

### 사고 — 테스트가 전부 통과하는데 프로세스가 죽었다

탭을 추가하자 mutation sweep 이 기준선에서 멈췄다("무력화 전부터 테스트가 실패한다").
그런데 돌려 보면 **478개가 전부 통과한다.** 종료 코드만 비0(`-1073740791` = 0xC0000409)
이었고, 그 값은 `bash` 에서 `127` 로 보여 더 헷갈렸다. PowerShell 로 돌려서야 원인이
나왔다 — `QThread: Destroyed while thread '' is still running`.

**창의 종료 경로가 페이지를 손으로 나열하고 있었다.** 새 탭이 그 목록에 없으니 폴러
`QThread` 가 살아남고, 파괴되면서 프로세스가 통째로 죽었다. `MainWindow.stop_all()` 이
등록된 탭 목록(`_pages`)에서 돌게 고쳤고, 목록이 뒤처지면 잡는 테스트를 붙였다.

**증상과 원인이 멀다**: sweep 은 "코드가 실패한다"고 말하지만 실패한 테스트는 없고,
진짜 원인은 테스트도 코드도 아닌 종료 경로였다. 같은 날 아침의 `pytest-current` 건과
같은 계열이다 — 둘 다 "전부 통과 + 종료 코드 비0"으로 나타났다.

  구분되지 않는 픽스처였다.
- `one_moment_once` — **중복 제거가 죽은 코드였다.** 같은 시각의 행들은 서로 간격이 0
  이라 간격 합산 방식에서 이미 0초를 더한다. 무력화해도 값이 안 변하는 게 당연했다.
  코드를 빼고, mutant 를 실제 보증자(간격 합산)를 겨냥하도록 바꿨다 — 그러자 관련
  테스트 4개가 함께 울었다. **검증할 수 없는 방어는 있으나 마나다.**

#### 4-B 예광탄 — GMM·HMM 을 기각한 근거 (2026-08-04)

**구현 전에 세 번 쟀고, 계획서의 기술 선택이 뒤집혔다.** 배관(마이그레이션·컴포넌트·UI)은
한 줄도 만들지 않았다 — 고칠 것이 전부 오프라인에 있었기 때문이다.

##### 1회차 — 계획서대로: 리소스 GMM(k-means) → 평활화 → foreground 로 명명

```
최고: k=10 · 평활 5분 · tol ±5분 →  경계 일치 61%    (DoD 90% · 미리 적은 실패선 70%)
```

**실패의 성격이 튜닝이 아니라 구조였다.** 클러스터가 게임과 비게임을 섞었다 —
`c0` = mahjong-jp 781분 + chrome 417분. `mahjong-jp`(cpu 20/gpu 18)는 **크롬으로 영상
보는 것과 리소스가 구분되지 않는다.** 게임 세션 109개 중 34개가 이 가벼운 게임이다.
평활화를 키우면 61% → 32% 로 나빠졌다(전환이 애초에 경계와 정렬돼 있지 않다는 뜻).

기각 근거는 여기서 이미 충분했다. 사전 조사에서 잰 변동계수가 그 이유를 설명한다 —
게임은 cv 0.14~0.34(이름이 곧 레짐), 범용 앱은 cv 0.62~1.85(이름 안에서 갈림).
**축의 순서가 반대였다.**

##### 2회차 — 축을 뒤집어 foreground 1차

61% → 77%(롤링모드 5분)로 올랐다. 리소스가 구조적으로 못 하던 일을 foreground 는 한다.
그런데 경계 정확도와 구간 길이가 정면 트레이드오프로 나왔고, **원인이 측정 쪽에 있었다.**

정답을 "게임이 foreground 인 구간"으로 잡았는데 DoD 문구는 "게임 **실행/종료**"다.
게임 도중 디스코드를 5분 보면 앞의 정의에서는 세션이 갈라져 경계가 둘 늘어나는데,
그건 실행도 종료도 아니다. **평활화는 정확히 그 알트탭을 지우는 일을 하므로,
평활화할수록 "경계 미스"로 집계됐다.**

##### 3회차 — 정답을 프로세스 생존 구간으로 (DoD 문구대로)

경계 217개 → **94개.** 알트탭이 123개를 부풀리고 있었다.

```
             방법        ±5분   ±10분   전환수   중앙길이   레짐내cv
  원본 foreground        99%    100%     1049       2분      0.38
     롤링모드 5분         93%     98%      534       6분      0.43
    롤링모드 11분         86%     97%      317      13분      0.46
   롤링+흡수 10분         71%     88%      158      32분      0.47
   레짐 없음(전체)                                            0.61
```

**일치율만 보면 안 된다.** 전환 534개/7,189분이면 ±5분 창에 우연히 걸릴 확률이 57%다.
리프트로 보면 롤링+흡수 10분(71% vs 우연 22% = **3.2배**)이 가장 깨끗하고 롤링모드
5분은 1.6배다. 1회차의 61%를 "전환이 잦아 우연히 맞은 것"으로 의심했던 것과 같은 검산이다.

##### 진짜 결론은 cv 열에 있었다

**평활화가 강할수록 cv 가 나빠진다**(0.38 → 0.49). 평활화는 "레짐다움"(긴 구간)을 사는
대신 **균질성과 경계 정확도를 함께 지불한다.** 그런데 균질성이 조건부 베이스라인의
목적 그 자체다.

여기서 되물으면 답이 나온다 — **베이스라인 조건부화에 시간 연속성이 필요한가?**
필요 없다. `chrome` 구간이 1,049조각으로 흩어져 있어도 합치면 1,729분이라 표본은
충분하다. 레짐을 "연속된 시간 덩어리"로 만드는 일(GMM·HMM·평활화)은 **UI 타임라인과
변화점 탐지에만 필요하고, 4-B 의 목적에는 불필요하다.**

```
계획서:  리소스 GMM → HMM 평활화 → foreground 로 명명 → (regime, hour) 베이스라인
확정안:  foreground 를 조건 변수로 그대로            → (program, metric) 베이스라인
         평활화는 표시용 타임라인에만 (롤링모드 5분, 93%)
```

cv 0.61 → 0.38 은 같은 편차에 대해 z 가 약 1.6배가 된다는 뜻이다. GMM·HMM 을 붙여
얻는 0.43~0.49 보다 **아무것도 안 붙인 쪽이 낫다.**

##### 곁가지로 확정된 것

- **`scikit-learn` 을 넣지 않는다.** 데이터가 7,189×9 라 순수 파이썬 k-means 로 충분했고,
  그마저 기각됐다. sklearn+scipy+numpy 는 PyInstaller 번들에 100MB+ 를 더한다.
- **`regimes` 테이블도 필요 없다.** 조건 변수는 `obs.processes` 의 `foreground` 플래그로
  이미 실시간·리플레이 양쪽에 들어오고, 과거 분석은 `metrics_1m.foreground_proc` 이 있다.
- **게임 목록을 코드에 둘 수 없다** — 배포 대상 PC 의 게임을 알 수 없다(설계 규칙 2).
  레짐 이름은 프로그램명 그대로 쓴다. 게임 목록은 예광탄의 정답 라벨 전용이었다.
- **이 수치는 이 PC 한 대·9일·게임 위주 사용이다.** 다른 하드웨어에서 같은 결론이
  나올지는 확인할 방법이 없다.

#### 1 — `MIN_DAY_HOURS`: 상수만 있고 판정이 없었다, 그리고 값도 틀렸다 (2026-08-04)

07-30 mutation 측정에서 "무력화해도 10개가 전부 통과"로 나왔던 셋 중 마지막 하나다.
다른 둘과 달리 **테스트가 없어서가 아니라 구현이 없어서** 안 잡혔다 — `xfail(strict)`
하나가 그 사실을 고정하고 있었다. `build()` 가 `days = len(by_day)` 로 날짜만 셌다.

짧게 켠 날이 하루로 세어지면 **"3일 이상 관측"이 사실상 "3번 실행"** 이 된다.
그 표본으로 세운 p99 는 그 프로그램의 평소가 아니고, 그 지문이 억제를 하면
진짜 누수가 묻힌다.

##### 값 6.0 은 전제가 틀린 값이었다

구현하고 실측하니 지문 179개 중 **74개(41%)가 탈락**했다. 탈락 목록이 이상해서 —
`ctfmon`·`esddiscord` 같은 상시 백그라운드가 9일간 하루 평균 4~5시간으로만 잡혔다,
PC 는 하루 10~19시간 켜져 있는데 — `ProcessRollup` 을 열어 보니 **버킷마다 상위 40개만
남긴다.** 즉 여기서 세는 버킷은 *켜 둔 시간*이 아니라 **활성 집합에 있던 시간**이다.

상수의 근거였던 "2시간 켜 둔 날과 12시간 켜 둔 날은 같은 하루가 아니다"는 관측 시간
해석이고, 그 해석으로 고른 6.0 이 활성 체류 시간에 걸리면 훨씬 강한 조건이 된다.

```
프로세스-일 1,534개의 하루 버킷 수:  p50 = 0.9h · p75 = 6.4h · 최대 17.4h(가동 상한)

min_day_hours   지문    프로세스종
        0~1.0    179          90     ← min_buckets=100 이 이미 하는 일
          2.0    165          83
          6.0    105          53     ← 계획서 값
```

**6.0 이 자르는 것은 게임 클라이언트였다.** 이 PC 의 게임 사용은 하루 1.4~2시간
(`deltaforceclient` 7일간 118버킷, `fczf` 9일간 226버킷)이라 6시간 문턱에 전부 걸린다.
지문을 잃는 37종 중 **8종은 실제 사건에 등장한 프로세스**다 — `fczf` 7건,
`leagueclient*` 18건, `deltaforceclient` 2건, `mahjong-jp` 1건.

게임은 핸들·RSS 변동이 커 `procleak` 오탐의 주 원천이다. 거기서 억제를 걷어내는 것은
**탐지 규칙 1(오탐이 미탐보다 비싸다)의 반대 방향**이다. 계획서가 "1 을 마지막에 두는
이유"로 적어 둔 우려가 정확히 이것이었고, 실측이 그 우려를 확인했다.

##### 1.0 으로 정한 근거

원래 의도(짧은 날 배제)를 달성하면서 **현재 지문을 하나도 잃지 않는다**(179개 유지).
0~1.0 구간에서 지문 수가 안 변하는 이유는 `min_buckets = 100` 이 이미 그 일을 하기
때문이다 — 지금 자격을 통과하는 것들은 모두 최소 3일은 1시간 이상 관측된다.
짧은 날만으로 자격을 넘보는 프로세스가 생기면 그때부터 이 조건이 실제로 일한다.

알림량이 늘지 않으므로 **리플레이 before/after 를 돌리지 않았다** — 동작이 같다.
계획서의 "평가 + 알림량 측정" DoD 는 6.0 을 전제한 것이고, 값이 바뀌면서 잴 차이가

있다(3일). 게임을 며칠 안 하면 지문을 잃는다 — 잃으면 그 게임에 대한 억제가 사라진다.

#### D — 5분 롤업이 46분 멈췄다 (2026-08-04)

**"데이터 잘 쌓이고 있나" 점검에서 나왔다.** 원시 수집은 멀쩡한데(간격 1.01초,
`drop_count` 0, CPU 0.22%) `process_5m`·`net_activity_5m` 만 46분째 갱신이 없었다.
`metrics_1m`(60초 주기)은 정상이라 티가 안 났다 — **주기가 긴 것부터 조용히 멈춘다.**

```
23:12  RSS 472MB > 예산 300MB, 3회 연속 → 스로틀 3 (배수 10.0)
23:42  롤업 실행 후 `self._stop.wait(3000)` — 50분 대기 진입
00:06  스로틀 0 으로 회복 — 그러나 이미 잠든 스레드는 깨지 않는다
```

`Event.wait()` 는 종료 신호에만 반응한다. **스로틀은 주기를 늦추라는 뜻이지, 회복된
뒤까지 늦춘 채로 두라는 뜻이 아니다.** 스로틀이 오르내릴 때마다 관측이 그만큼 비었다.

##### 순서에 인과가 있었다 — 관측 도구가 먼저

1·2·3 을 나열이 아니라 **1이 없으면 3이 헛돈다**는 순서로 짰고, 실제로 그랬다.

| # | 한 일 | 왜 그 자리였나 |
|---|---|---|
| 1 | 로그레벨 자리 복구 | 이걸 안 고치면 3번 관측이 헛돈다 |
| 2 | 스로틀 회복 시 깨우기 | 1번으로 관측이 되어야 효과를 잰다 |
| 3 | 실행 중 컴포넌트 계측 | 2번은 증상만 막는다. 원인은 이게 남는다 |

**1번이 이 사고를 늦게 알아챈 진짜 이유였다.** `extra={"level": 3}`(스로틀 단계)이
JSON 로그의 로그레벨 자리를 덮어써 예산 초과 경고가 `"level": 3` 으로 찍혔고,
`level=WARNING` 으로 거른 점검에서 **전부 누락됐다.** 08-04 점검에서 실제로 놓쳤다.
기존 예약키 테스트는 `LogRecord` 속성만 봐서 이걸 못 잡는다 — `level` 은 속성이 아니라
(속성명은 `levelname`) 검사를 통과하는데 **JSON 출력에서만 이름이 겹쳐, 예외 없이
값만 틀어졌다.** 포매터가 자기 자리를 지키고 충돌한 `extra` 는 `extra_*` 로 옆에 둔다.

##### 2번 — 잘게 자른 대기, 값은 실측으로

`threading.Event` 둘을 함께 기다리는 방법은 파이썬에 없다. 남은 대기를 매 틱
재계산하는 루프로 갔다 — 배수가 내려가면 일찍 깨고 올라가면 더 잔다(양방향).

**`wake_granularity_s` 를 15.0 으로 잡으려다 실측 후 5.0 으로 내렸다.**
`Event.wait` 타임아웃 1회가 CPU **7.8µs** 라, 컴포넌트 10개가 하루 17만 회 깨어나도
**0.0016%** — 예산 2% 의 1/1000 이다. "예산 초과 상황에서 늘리는 대기이니 크게 잡는다"는
처음 논리는 **비용이 실제로 얼마인지 모르고 세운 것**이었다. 비용이 없으면 관측이
비는 시간을 줄이는 쪽이 맞다.

##### 3번 — 봉우리를 더 자주 찍지 않고, 누가 돌고 있었는지를 남긴다

예산 초과 시점의 실측 RSS 는 **447 / 469 / 553 / 588MB**(상한 300)인데 `self_telemetry`
평균은 65MB 이고 `private_mb` 는 501MB 로 평탄하다. **순간값만 튄다** — 5초 표본이
봉우리를 놓치고 있다는 뜻이다.

여기서 표본 주기를 줄이는 것은 **관측자가 예산을 먹는 방향**이라 규칙 1 에 걸린다.
tick 마다 RSS 를 재는 델타 측정도 psutil 호출이 초당 수십 번 늘어 같은 이유로 뺐다.
대신 `Supervisor` 가 `_active` dict 를 유지해(tick 당 쓰기 두 번) **표본을 찍은 그
순간 tick 중이던 컴포넌트**를 `self_telemetry.active` 에 남긴다(마이그레이션 013).
스로틀 표본만 모아 분포로 보면 범인이 드러난다.

**계측이 거짓말할 수 있는 자리 둘을 테스트로 막았다.** 예외로 끝난 tick 을 `finally`
없이 지우면 한 번 터진 컴포넌트가 영원히 "실행 중"으로 남아 **모든 표본에 그 이름이
박힌다** — 아무나 가리키는 계측은 없는 것보다 나쁘다. 그리고 조회 실패가 계측 자체를
멈추면 예산·누수 판정의 유일한 근거가 사라지므로, `active` 조회는 실패해도 행은 쓴다.

##### 판단을 미룬 것

**예산 300MB 를 올릴 것인가는 정하지 않았다.** 설계 규칙 1 에 직접 걸리는 값이라
데이터 없이 올리면 "모니터가 병목이 되지 않는다"는 약속이 숫자만 커진 채로 남는다.
`throttle_level > 0` 표본의 `active` 분포를 보고 판단한다(조건은 `PLAN.md` §8).

#### 15 — 사건의 자원·제목이 탐지기의 주장을 버린다

14번 4건 모두 **신호는 `handles`/`python` 인데 사건은 다른 자원으로 발표됐다.**

| 사건 | 병목 | attributable | 자원 | 제목 |
|---|---|---|---|---|
| #42 | CONTENTION | False | cpu | 경합 — 컨텍스트 스위치 평소의 8.1σ |
| #43 | CONTENTION | False | cpu | 경합 — 컨텍스트 스위치 평소의 4.1σ |
| #44 | MEMORY | True | rss | 메모리 압박 — python 30% |
| #45 | CONTENTION | False | cpu | 경합 — 컨텍스트 스위치 평소의 19.7σ |

**원인은 8번 수정의 조건절이다.** `fusion.py:236`·`fusion.py:277` 이 탐지기의 주장(`claim`)을
`bottleneck.kind == "NONE"` 일 때만 쓴다. 오전 4건은 전역 지표가 조용해 `NONE` 이었고 그래서
통과했지만, 이번에는 분류기가 **뭔가를 찾아냈다** — 그러자 claim 이 통째로 버려지고 자원이
`cpu`/`rss` 로 돌아가 귀인이 엉뚱한 축에서 돌았다.

**그 "뭔가"는 주입과 인과가 없다.** 주입 구간의 컨텍스트 스위치 중앙값이 오히려 더 낮다
(28,431/s vs 구간 밖 103,580/s, n=2,723/2,339). 분류기는 구간 안의 **최악 시점 한 점**을
잡는데 그 점이 유튜브·크롬의 잡음이었다. `_peak_and_baselines` 의 구조상 긴 구간에서는
무관한 스파이크가 항상 하나쯤 잡힌다.

**설계 논점 (합의할 것).** 조건을 `NONE` 에서 무엇으로 넓히는가.

- **안 (가) `attributable` 로 바꾼다.** CONTENTION·GPU·THERMAL·NONE 은 `_RESOURCE_BY_KIND`
  에서 이미 `attributable=False` 다 — **제품이 스스로 "이 병목은 프로세스로 설명되지
  않는다"고 선언한 것들이다.** 그 상태에서 탐지기가 프로세스와 문장을 갖고 있으면 그쪽이
  낫다는 것은 8번에서 이미 합의한 논리이고, 조건만 한 칸 넓히는 것이다. 3건(#42·#43·#45)이
  이것으로 해결된다.
- **미해결로 남는 것: MEMORY(#44).** `attributable=True` 이고 1위도 마침 `python` 이라
  프로세스는 맞았지만 자원과 설명이 틀렸다(주입기가 핸들을 들면 RSS 도 조금 오른다).
  여기서 claim 을 이기게 하려면 **"구체적 병목이 있어도 탐지기가 이기는" 규칙**이 필요한데,
  그건 `CPU 병목 — chrome 68%` 를 프로세스 내부 사정으로 덮을 위험을 연다. 8번에서
  일부러 피한 방향이다.
- **판단 필요:** (가)만 하고 MEMORY 는 남길지, 아니면 claim 의 점수·지속시간으로 겨루게
  할지. 후자는 새 문턱이 생기므로 `config` 로 나가야 한다(규칙 3).

**구현한 것 (2026-08-02) — (가)를 좁혀서 넣었다.** 조건은 `attributable` 이 아니라
`_CLAIM_WINS_OVER = {"NONE", "CONTENTION"}` 이다. (가)는 `attributable=False` 인 넷을 한
덩어리로 묶지만 **성질이 둘로 갈린다.**

| 종류 | 무엇을 말하는가 | 주장에 양보하는가 |
|---|---|---|
| `NONE` | 전역 지표에서 아무것도 못 찾았다 | 예 |
| `CONTENTION` | 정의상 **어떤 자원도 포화되지 않았다** — `_RESOURCE_BY_KIND` 주석도 "CPU 상위는 참고일 뿐" | 예 |
| `GPU`·`THERMAL` | 특정 하드웨어 상태를 **실제로 관측했다**(92°C, 실효 클럭 저하) | **아니오** |

`GPU`·`THERMAL` 까지 넓히면 `발열 스로틀링 — GPU 92°C` 가 프로세스 하나의 핸들 이야기로
대체된다. 읽는 사람은 그 프로세스를 의심하지만 GPU 를 태운 것은 게임이다 — 8번이 제목에서
프로세스를 뺀 것과 같은 이유이므로, 여기서 되돌리면 그 수정을 무효로 만든다.

**MEMORY(#44)는 손대지 않았다.** 판단 필요 항목 그대로 남는다. 16번 배치의 새 사건에서
이 계열이 몇 건 나오는지 세어 숫자와 함께 다시 올린다.

**테스트가 처음에 아무것도 보지 않았다.** 경합 시나리오를 만들었는데 분류가 `CONTENTION`
이 아니라 `NONE` 을 냈고, `NONE` 은 원래 주장을 채택하므로 **규칙을 지워도 통과했다.**
원인은 `_peak_and_baselines` 가 `max(rows, key=cpu_total)` 로 **한 행**만 뽑고 분류기가
그것만 본다는 것이다 — 컨텍스트 스위치 스파이크의 CPU 도 함께 올려야 그 행이 뽑힌다.
(이 구조가 15번 문제의 원인이기도 하다. 12분 구간에서 무관한 스파이크 한 점이 분류를
통째로 결정한다.) 이제 테스트가 `bottleneck == "CONTENTION"` 을 먼저 고정한다.

**DoD 가 성립하지 않게 됐다 (2026-08-02).** 원래 계획은 "저장된 4건을 `analyze_incident()`
로 재분석해 판정한다 — 읽기 전용이라 재주입 불필요"였다. 그 사이 이틀이 지나 **근거 데이터의
절반이 보존 정리에 지워졌다** — 17번 참조. `process_metrics` 는 보호되어 남았지만
`metrics_raw`·`gpu_metrics` 가 없어 재분석이 병목을 관측하지 못한다. 지금 돌리면 4건 모두
`자원 cpu / 제목 "관측 없음" / 기여자 0` 이 나오고, 이는 15번의 증거가 아니라 채점 불능이다.

**그래서 순서가 바뀐다: 17(완료) → 16(재실행으로 새 데이터 확보) → 15(판정·합의).**
16번의 배치가 끝나면 그 구간이 이제 네 테이블 모두 보호되므로, 15번을 며칠 뒤에 판정해도
같은 일이 반복되지 않는다.

| 단계 | 기준 | 지금 |
|---|---|---|
| 필수 | 4건 모두 자원이 `handles`, 1위 기여자가 `python` | 0/4 |
| 목표 | 제목이 탐지기 문장 — `python (PID …) 핸들 704 → 3,832개 (5.4배, …)` | 0/4 |
| **회귀** | `CPU 병목 — chrome 68%` 류가 프로세스 내부 사정으로 덮이지 않는다 | 지켜야 함 |

**16번 배치로 판정한 결과 (2026-08-02 14:15~16:14, 8회차) — (가)는 이번 데이터에 0건 적용됐다.**
새 사건 8건이 전부 `CONTENTION` 이 아니라 **`MEMORY`** 로 분류됐다. `MEMORY` 는

#### 18 — 스왑이 0 이 아니면 항상 메모리 병목이 된다 (2026-08-02 발견, 다음 1순위)

대상인 Windows 에서는 항상 참이다. 규칙 1(오탐은 미탐보다 비싸다)에도 걸린다 — 이 한
줄 때문에 제품 경로 귀인이 12.5% 다.

**제안:** 다른 지표와 같은 형태로 맞춘다 — `swap_z >= z_high` 를 요구해 **평소보다 스왑이
크게 늘었을 때만** 점수를 준다. `z_high` 는 이미 있는 값이라 새 문턱이 생기지 않는다
(규칙 3 을 건드리지 않는다). 절대 하한(`swap >= N MB`)을 쓰는 안은 기계마다 페이지파일
크기가 달라 규칙 2 에 다시 걸린다.

**고친 것 (2026-08-02 17:1x).** 조건을 `if swap:` → `if swap and (mem or 0) >= 60.0:` 으로
바꿔 **스왑을 독립 근거에서 보조 근거로 강등**했다. 스왑이 압박의 신호이려면 "메모리가
부족해서" 페이지아웃이 일어나야 하는데, Windows 의 페이지파일 사용량은 압박과 무관하게
존재한다. 진짜 신호는 페이지폴트 **속도**지 사용량이 아니고, 그건 지금 수집하지 않는다.

**`swap_z >= z_high` 안은 채택하지 않았다.** 스왑은 값이 거의 일정해 산포가 작고, 448 →
449 가 큰 z 로 계산된다 — 디스크 응답의 `0.1 → 0.2ms = 20σ` 와 같은 함정이다. 같은 파일
`DISK_RESP_FLOOR_MS` 주석이 이미 그 교훈을 적어 두고 있었다.

#### 17 — 주입 구간에서 전역 지표가 지워져 채점이 불능이 된다 (완료 2026-08-02)

07-30 에 끊긴 세션의 마지막 명령(`python -m argus.eval --attribution`)을 08-02 에 돌려 나온 것이다.

```
제품 경로 1순위 지목률 :  0/7  =   0.0%   [FAIL]
```

제품 경로 7건이 **전부** `자원 cpu / 제목 "관측 없음" / 기여자 없음` 이었다. 15번(claim 버림)
으로는 설명되지 않는다 — 저장된 사건에는 `경합 — 컨텍스트 스위치 8.1σ` 라는 제목이 남아

`FAULT_PROTECTED = ("process_metrics", "process_events")` — **주입 구간에서 지키는 것이
절반뿐이었다.** 채점은 네 갈래를 함께 읽는다: 기여도(`process_metrics`), 정답 PID 트리
(`process_events`), 그리고 **병목 분류(`metrics_raw`·`gpu_metrics`)**. 뒤의 둘이 24시간
(`raw_hours`) 만에 지워져, `analyze_incident()` 가 병목을 관측하지 못하고 자원을 기본값으로
되돌렸다. 실측:

```

gpu_metrics      08-01 14:06 ~ 08-02 14:08    07-30 주입 구간 = 0행
process_metrics  07-29 20:37 ~ 08-02 14:06    07-30 주입 구간 = #44 343행 … #47 118행
```

**이 실패는 조용하다.** 정리는 정상 종료하고, 로그의 `fault_windows_held` 도 정상이며,
라벨과 프로세스 행은 멀쩡히 남아 있다. 채점을 돌릴 때에야 수치로 나타나는데 그때는 이미
데이터가 없어 원인과 결과를 잇기 어렵다 — 실제로 이번에 "탐지가 퇴행했다"로 읽힐 뻔했다.

고침은 목록에 둘을 더한 것이고, `tests/test_retention_fault_tables.py` 가 세 가지를 고정한다:
구간 안 행이 세 테이블 모두 남는다 / 구간 밖 기한 초과 행은 그대로 지워진다(아무것도 안
지우는 정리로는 통과하지 못한다) / 보호 목록이 채점이 읽는 이름을 덮는다. 둘을 빼고 돌려
앞의 것과 목록 테스트가 실패하는 것을 확인했다(나머지 5건은 통과 — 구간 길이 규칙은 무관하다).

**보호 비용은 작다.** 주입 구간은 12분짜리 몇 개뿐이고 두 테이블 모두 1초 간격이라 구간당
수백 행이다. 대신 그 구간은 `raw_hours` 와 무관하게 영구히 남으므로, 주입 라벨을 남발하면

#### 8 의 설계 (착수 전 합의할 것)

배관은 이미 있다. `fusion.py:89` 가 `incident_signals` 조인으로 **신호의 `features` 를
이미 읽고 있고**(`features["evidence"]` 로 지표 이름까지 훑는다), `procleak` 의 features

정할 것 셋:

1. **자원 우선순위.** 병목 분류기가 `NONE` 을 내면 **탐지기가 말한 자원을 쓴다.**
   구체적 병목(CPU·IO·MEMORY)을 내면 그것을 유지한다 — 전역 지표가 실제로 증상을

2. **탐지기가 여럿일 때.** 한 사건에 `procleak`(handles)과 `rules`(cpu)가 섞이면

   내려간다. 탐지기끼리 충돌하면 점수가 높은 쪽.
3. **`NONE` 의 `attributable`.** 지금 `_RESOURCE_BY_KIND["NONE"] = ("cpu", True)` 다.
   GPU·THERMAL 은 CPU 로 내려갈 때 `False` 로 "모른다"를 실어 보내는데, **"병목을
   모르겠다"는 NONE 이 확신을 갖고 CPU 기여자를 내놓는 것은 앞뒤가 맞지 않는다.**
   탐지기 자원이 있으면 그것으로 `True`, 없으면 `False` 로 바꾼다.

**(가) 활성 집합에 핸들 축이 없다.** `collector.process` 는 CPU 상위 15 + 메모리 상위 10 +

어긋남이다.

후보 셋 — **저장량과 탐지를 맞바꾸는 결정이라 합의가 필요하다.**

| 안 | 방법 | 비용 |
|---|---|---|
| 핸들 상위 N 추가 | `top_handles: N` | 상시 핸들이 많은 프로세스만 잡힌다. 400개에서 시작하는 누수는 여전히 못 본다 |

**채점이 채점 대상을 망가뜨린다.** 실사용에서도 같다 — 누수가 반복되는 프로그램은 누수가
"평소"가 된다. 대책 후보: 지문 생성에서 결함 주입 구간을 제외한다(라벨이 이미 있다),
또는 지문에 "이 값이 정상이라는 근거"의 신뢰도를 넣는다.

#### 12 (최초 기록) — 주입 7건 중 3건은 사용자가 아무것도 받지 못한다 (2026-07-30 13:5x)

| 가설 | 근거 | 상태 |
|---|---|---|

같은 일이 생긴다: 누수가 반복되는 프로그램은 누수가 "평소"가 된다.

**왜 4건은 발화했는가도 답해야 한다.** 같은 지문·같은 규모인데 절반만 발화한 이유를

#### 2 를 3 에 흡수한 이유 (2026-07-30 실측)

디스크 룰은 **이 PC 에서 전 기간 0건 발화했다.** NVMe 라 중앙값이 0.093ms 이고 3ms 를
넘는 순간이 24시간에 28번뿐이며 최장 연속이 6표본이라, 지속 조건 30초에 닿을 수 없다.
**3 이든 5 든 이 PC 에서는 영원히 안 울린다** — 값을 고르는 데 쓸 검증 수단이 없다.

그래서 5ms 통일은 **성능 이득이 아니라 일관성 확보**로만 진행한다(코드 변경이 작아
3번에 함께 넣는다). 실제 이득은 배포 대상에서 나온다 — HDD·SATA 사용자는 이 룰이
발화하고, 3~5ms 구간에 걸리면 **울리면서 병목 판정은 디스크가 아니게** 되어 8번의
증상을 그대로 탄다. 그 경로를 하나 막는 것이다.

**재보니 더 큰 문제가 있다.** 상대 조건 `median + 6*sigma` 가 이 PC 에서 **0.413ms** 다.
디스크가 조금이라도 일하면 넘으므로, 주석이 "둘 다 요구한다"고 말하는 AND 조건이
NVMe 급에서는 **사실상 절대값 단독 판정**이다. 규칙 2 가 이 룰에서 성립하지 않는다.

설계한다.** 지금 데이터는 NVMe 한 대뿐이어서 근거가 부족하다.

#### 규칙 2 위반 — 하드웨어 가정 (GPU 온도 해소 2026-08-02, 나머지 대기)

`ctx_switches_ps > 50000`(코어 수 의존), `swap_used_mb > 512`(RAM 의존)에
`machine_profile` 정규화가 없다. **GPU 온도 룰(80/90/95)은 상대 조건이 아예 없었다** —
다른 룰은 전부 `median + k*sigma` 를 AND 로 거는데 이것만 절대값이었다.

**GPU 온도는 노트북 얘기가 아니라 이 PC 에서 이미 오탐이었다.** 실측(5.9일, 표본 65,695):

```
GPU 온도  중앙값 83도 · p95 92도       80도 초과 52.6% · 90도 초과 19.7%
발화      GPU 열 스로틀링 55건 + 고온 지속 16건 = 하루 12.7회
          `rules` 신호 117건 중 GPU 룰이 75건 (64%)
```

`GPU 열 스로틀링`(80도, info)을 없애고 `GPU 고온 지속`(90도)에 `median + 3*sigma` 를
AND 로 걸었다. 없앤 룰은 주석에 스스로 "부하 시 흔한 동작이다"라고 적어 두고 그것을
알리고 있었다. `k=3` 인 이유: GPU 온도는 σ 가 4.2도로 커서 디스크(6σ)·ctx(8σ) 같은 큰
값을 쓰면 `median + 25도`가 되어 어떤 값도 넘지 못한다.

**이 발화들이 오탐이라는 것을 웜 데이터로 확인했다.** GPU 부하 구간(`gpu_util_mean >= 80`)

올라간다 — 전혀 안 움직인다. 93도가 이 GPU 의 열 평형점이고 90도 문턱은 그 아래였다.

**효과** (평가용 스냅샷, 같은 입력): `rules` FP 4 → **0**, 오탐/시간 0.97 → 0.00.
`procleak` 은 8/2/0 그대로. `GPU 위험 온도`(95도)는 유지 — 실리콘 안전 한계는 벤더가
정하고 사용자 PC 마다 다르지 않다.

#### Streamlit 제거 — ✅ 2026-08-09 완료

**순서를 지켰다: 안내를 먼저 옮기고, 그다음 지웠다.** 반대로 했으면 격차가 있는 구간이
생기고 그 구간에 되돌릴 이유가 발생한다.

```
1b26135  feat(desktop) 첫 실행 안내를 창으로 (mutation 3/3 잡힘)
9eeb98f  refactor(ui)  Streamlit 판 삭제 — 1,089줄
```

남긴 것은 `data.py`·`theme.py` 뿐이고 **패키지 이름은 `dashboard/` 그대로 뒀다** —
바꾸면 `desktop/` 전체의 import 가 함께 움직여 삭제와 이름 변경을 한 번에 되돌리게
된다. 이름 변경이 필요하면 별도 커밋이 맞다.

`theme.py` 에서 plotly 전용 `layout()`·`line()` 과 쓰이지 않던 `severity_color()` 도
함께 지웠다. **UI 를 지웠는데 그 UI 전용 헬퍼가 남으면, 다음 사람이 그것을 보고
쓰이는 줄 안다.**

아래는 착수 전에 세워 둔 조건과 그 판정이다(기록으로 남긴다).

지우는 것은 **되돌리기 어려운 유일한 단계**라 서두르지 않았다.

- **사람이 두 UI 를 나란히 놓고 비교했는가.** 지금까지 검증은 "몇 개를 그렸는가"였고
  그것은 갱신이 도는지만 말한다. 같은 구간을 두 화면에서 열어 **수치가 같은지** 봐야 한다.
- **네이티브에 없는 것이 있는가.** 자기 상태 페이지의 시스템 이벤트·평가 이력은 아직
  안 옮겼다(`4_자기상태.py` 후반부).
- **`dashboard/data.py`·`theme.py` 는 남긴다.** 조회 계층은 두 UI 가 공유하고, 네이티브가
  그대로 쓴다. 지우는 것은 `dashboard/pages/`·`app.py`·`common.py` 와 Streamlit 의존뿐이다.
- 지우면 `pyproject` 에서 streamlit·plotly 를 뺄 수 있고 상주 exe 의 `excludes` 도 정리된다.

##### 확인 결과 (2026-08-09) — 조건 셋 중 둘 충족, 하나는 격차 하나가 남았다

**수치가 같은가 — 눈이 아니라 구조로 답한다.** 두 UI 가 `data.py` 함수를 **1:1 로 같이**
쓰고, 어느 쪽도 자기 쿼리를 따로 만들지 않는다(양쪽 다 `sqlite3`·`.execute(` 가 0곳).
기본 구간까지 같다 — 타임라인 6시간 · 프로세스 60초 · 자기 상태 8시간 · 사건 7일.

```
실시간   latest_metrics · latest_gpu · recent_metrics(600) · recent_gpu(600)   동일
타임라인 rollup · anomaly_signals · fault_injections (hours 동일)              동일
프로세스 top_processes(limit=20) · process_series(1800)                        동일
자기상태 9개 함수 전부                                                          동일
사건     incidents · set_user_label                                            동일
```

**같은 함수에 같은 인자면 같은 값이다.** 나란히 놓고 보는 것은 이보다 약한 검사다 —
사람 눈은 두 화면의 수치가 소수점에서 갈리는 것을 못 잡는다.

**네이티브에 없는 것 — 위 항목은 낡았다.** 시스템 이벤트·평가 이력(탐지기 스코어보드)은
`selfstate.py:173-198` 에 이미 있다. 08-09 캡처로 표 두 개가 실제로 그려지는 것까지 봤다.

**남은 격차는 하나다 — 첫 실행 안내.** → ✅ 옮겼다(`1b26135`). Streamlit 홈은 DB 가 없으면 *"데이터베이스가
없습니다. `python -m argus` 로 수집을 먼저 시작하세요"* 를 경로와 함께 띄운다. 네이티브는
페이지마다 "…기다리는 중"으로 남아, **아직 안 쌓인 것과 고장난 것이 구분되지 않는다**
(설계 규칙 4 — 조용히 실패하지 않는다). **배포 대상 사용자가 처음 보게 될 화면이라
지우기 전에 이것부터 옮긴다.**

- 사이드바의 "수집 상태"도 홈에만 있다. 네이티브는 상태 표시줄이 `표본 N개 · 최신 N초 전`
  을 항상 보여 주므로 대체됐고, 롤업 워터마크는 자기 상태 페이지에 있다. 격차 아님.
- `pyproject` 에 **streamlit·plotly 가 애초에 없다**(specs 의 `excludes` 에만 있다).
  지워서 줄어드는 의존성은 없다 — 줄어드는 것은 코드 1,089줄(`pages/` 933 + `app.py` 69
  + `common.py` 87)과 UI 두 벌을 함께 고쳐야 하는
  부담이다(`data.py` 를 고칠 때 양쪽 호출부를 봐야 하는 것).

**이식하며 알게 된 것**

- **백필과 실시간을 따로 세야 한다.** 합쳐 세면 "창을 열었다"와 "갱신이 돈다"가
  구분되지 않는다 — 첫 측정 608개 중 600개가 백필이었고 실시간은 8개뿐이었다.
- 페이지마다 **데이터 성격이 달라 백필 전략도 다르다.** 실시간은 10분/초 단위지만
  타임라인은 24시간/분 단위라 그대로 옮기면 안 된다.
- 표 중심 페이지(프로세스·사건)는 차트와 위젯이 다르다. `QTableView` + 모델을
  한 번 만들어 두면 둘이 공유한다. → **2026-08-03 확보** (`desktop/widgets.py`).
- **`setSortingEnabled(True)` 는 즉시 0번 열 내림차순으로 정렬한다.** 조회 순서를
  지키려면 인디케이터를 `-1` 로 꺼야 한다. 프로세스 표가 CPU 순 대신 이름 역순으로
  뜨던 원인이고, **눈으로 보면 그냥 넘어간다.**
- **Qt 객체를 테스트에서 GC 시키면 인터프리터가 죽는다**(`QThread` 를 물고 있을 때).
  `tests/test_desktop.py` 의 `_KEEP` 가 그것을 막는다 — 세션 끝에 비우는 것도 안 된다.
- 표 테스트는 **데이터를 고를 때 조심한다.** 조회 순서와 정렬 결과가 우연히 같으면
  규칙을 지워도 통과한다(실제로 그렇게 썼다가 mutation 에서 드러났다).
- **`isVisible()` 로 위젯 표시를 검증하지 않는다.** 부모 창이 `show()` 되어야 True 라,
  창을 띄우지 않는 테스트에서는 **항상 False** 다 — 아무것도 검증하지 못한다.
  명시적 숨김 여부를 보는 `isHidden()` 을 쓴다.
- **"있는가"와 "부르는가"는 다르다.** 08-03 에 두 번 같은 실수를 했다 — 정렬 테스트는
  데이터가 우연히 같아서, 캐시 테스트는 `cache_clear` 의 *존재*만 봐서 각각 헛돌았다.
  둘 다 mutation 이 `[안 잡힘]` 으로 드러냈다. **새 테스트는 반드시 mutation 으로
  확인한다** — 이 둘은 통과만 보고 넘어갔으면 그대로 남았을 것이다.
- UI 이식 중 발견한 회귀는 **Streamlit 판에도 있다.** 두 UI 가 같은 `data.py` 를
  쓰므로, 조회 계층을 고칠 때는 양쪽 호출부를 함께 본다(피드백 `cache_clear` 가 그랬다).

**이식할 때 알아 둘 것**

- `data.py`(286줄)·`theme.py`(102줄)는 **그대로 쓴다.** 캐시를 `ttl_cache` 로 바꿔
  UI 의존을 떼어 놨다.
- 차트는 plotly → pyqtgraph 로 다시 그린다. plotly 를 Qt 에서 쓰려면 WebEngine 이
  필요한데 그건 번들 크기를 300MB 더 늘린다.
- **실시간성 검증을 숫자로 한다.** `--seconds N` 이 그동안 그린 표본 수를 돌려준다.
  눈으로 보면 "굼뜬가?" 로 넘어간다 — 실제로 첫 실행에서 그럴 뻔했다.

**2 에서 남은 것**

- **눈으로 확인**: 트레이에 아이콘이 보이는가, 풍선이 뜨는가, 우클릭 메뉴 두 항목이
  도는가. **반환값은 "Windows 가 요청을 받았다"까지만 증명한다.** 사람이 봐야 하고
  자동화하지 않는다(마우스를 움직이지 않는다). Windows 는 새 트레이 아이콘을 기본으로
  숨기므로 "숨겨진 아이콘" 영역까지 봐야 한다.
- **`console=False` 로 바꿀지 판단.** 지금 exe 는 콘솔 창이 뜬다. 없애면 사용자 경험은
  나아지지만 **기동 실패 메시지도 안 보인다** — 그리고 오늘 `FingerprintBuilder` 버그를
  잡은 것이 정확히 그 콘솔이다. 크래시 파일만으로 충분한지 확인한 뒤에 끈다.
- **알림을 실제로 켤지.** 코드는 준비됐고 `detection.notify` 는 여전히 `false` 다.
  근거는 쌓이는 중 — **20번 수정 이후 누적 약 8시간(121분 게임 세션 포함) 알림 0건**.
  며칠 더 보고 정한다.

**전제가 하나 바뀌었다 — 알림량 측정은 이미 시작됐다.** §8 은 "1번(`MIN_DAY_HOURS`)
구현 후 알림량 측정"을 켜기 전 조건으로 뒀는데, 판정(`notified`)과 발송을 분리해
두었으므로 **지금 상태로도 계속 측정된다.** 1번은 알림을 늘리는 변경이라 오히려
나중이 맞다.

#### 1 을 마지막에 두는 이유

`MIN_DAY_HOURS` 를 구현하면 자격을 통과하는 지문이 **줄고**, 지문이 줄면 `procleak`
억제가 **약해져 알림이 늘어난다.** 오탐이 미탐보다 비싸다는 규칙과 반대 방향이다.
07-30 최근 2시간에 사건 7건 중 5건이 알림 대상으로 판정됐으므로 **이미 양이 많다.**

그래서 8·10 을 고쳐 알림의 내용과 등급이 정리된 **뒤에 양을 측정하고**, 그 수치를 보고
1 을 넣을지 판단한다. DoD 에 "구현했다"가 아니라 **"구현 후 시간당 알림 대상 건수"** 를
포함한다. 늘어난 알림이 전부 옳은 알림이면 받아들이고, 아니면 억제 쪽을 함께 손본다.

#### 7 — 지속되는 이상은 스스로 정상이 된다

6 을 고쳐도 남는 문제다. 베이스라인 창이 1800초인데 게임을 30분 넘게 하면 **부하가
창의 과반**이 되어 중앙값이 부하 쪽으로 옮겨간다. 중앙값은 표본의 절반이 망가져도
버티지만 절반을 넘으면 버티지 못한다. 그러면 실제 스로틀이 z ≈ 0 으로 묻힌다.

`_score()` 가 `abs(z)` 를 쓰는 것도 같이 봐야 한다. 위 10:09:14 의 z 는 **−0.47**,
즉 평소보다 **낮은** 값인데 점수가 붙었다. 방향을 잃은 점수는 등급의 근거가 되지 못한다.

이 둘은 **절대 조건으로 발화하고 상대 조건으로 등급을 매기는 조합**의 모순이다.
GPU 온도 룰(80/90/95)이 그 대표였다.

**절반은 20번에서 해소됐다 (2026-08-02).** GPU 온도 룰은 이제 상대 조건을 AND 로 걸고
(`median + 3 * sigma`), 절대값만 보던 `ctx`·`swap` 도 머신 상대값이 됐다. 발화 쪽의
모순은 없어졌다.

**남은 것은 두 가지고, 이쪽이 어렵다.**

1. **베이스라인 자정상화** — 창이 1800초라 게임을 30분 넘게 하면 부하가 "평소"가 된다.
   냉각 열화 탐지(20번)를 30분 롤링이 아니라 **일 단위 비교**로 만든 것이 이 문제를
   피해 간 것이다. 룰 엔진 쪽은 그대로 남아 있다.
2. **`_score()` 의 `abs(z)`** — 평소보다 **낮은** 값에도 점수가 붙는다(실측 z = −0.47).
   방향을 잃은 점수는 등급의 근거가 되지 못한다. 10번(등급 축)과 같이 봐야 한다.

**5 는 4 를 하면서 드러난 것이다.** 각 수집기의 `describe()` 가 건강 상태를 들고 있지만
**그 값을 읽는 것은 단독 스모크뿐이고 대시보드로 가지 않는다.** GPU 조회가 죽으면 이제
WARNING 로그와 복구 시도는 생겼지만, 사용자가 대시보드에서 "GPU 수집이 지금 실패 중"을
볼 수는 없다. 규칙 4 의 "드러내 놓고"를 완전히 만족하려면 이 경로가 필요하다.
`capabilities` 가 JSON 파일(`capabilities_path()`)로 저장되는 전례가 있어 같은 방식이
가능하지만, 누가 언제 쓰고 대시보드가 어떻게 읽는지는 별도 설계 사안이다.

**1 의 수정안** — 필요한 데이터가 이미 있다. `process_day_index()` 가 `{날짜: 5분 버킷 수}`
를 주므로 6시간은 72버킷이다.

```python
# 현재 (fingerprint.py:114)
days = len(by_day)
# 고친 뒤
days = sum(1 for buckets in by_day.values() if buckets >= MIN_DAY_HOURS * 12)
```

자격을 통과하는 지문이 줄고, 지문이 줄면 `procleak` 억제가 약해져 알람이 늘 수 있다.
그래서 리플레이 평가로 영향을 확인한 뒤 올린다. 통과하면
`tests/test_fingerprint.py` 의 `xfail(strict)` 표시를 **지워야 한다**(strict 라 통과가
실패로 뜬다 — 일부러 그렇게 뒀다).

**2 는 판단 사안이다.** `rules.yaml:82` 의 `disk_resp_ms > 3` 과 `bottleneck.py:92` 의
`DISK_RESP_FLOOR_MS = 5.0` 이 어긋나 **3~5ms 구간에서는 "디스크 응답 저하" 알림이
울리면서 병목 판정은 다른 자원으로 간다.** 두 파일의 주석이 모두 "체감 하한"이라는
같은 개념을 말하므로 의도가 갈린 것이 아니라 한쪽이 틀린 것이다. 5ms 를 권한다 —
NVMe 에서 0.1→0.2ms 가 20σ 로 병목 판정된 실측이 `bottleneck.py:88` 에 적혀 있어
3ms 로 내리는 것은 그 실측을 거스른다. 룰 표현식은 config 를 참조할 수 없으므로
값은 두 곳에 두고 **어긋남을 테스트로 막는다**(참조 기능을 만드는 것은 과하다).

**3 의 대상** — `explain` 섹션: `disk_resp_floor_ms`·`override_ratio`·`override_margin`·
`stock_drop_reset_ratio`, `fusion` 섹션: `extend_before_s`·`extend_after_s`,
`detection` 섹션에 `score_saturation_z`. 모듈 상수는 함수 기본값으로 남긴다 — 없애면
단독 실행 스모크가 config 없이 못 돈다. 지문 자격(`min_days`·`min_buckets`)은 이미
`__main__.py:288` 에서 연결돼 있어 **위반이 아니다**(07-30 점검 기록의 오류).

## THERMAL 축은 조건이 아니라 공급이 막혀 있었다 (2026-08-19 밤)

`readiness.py` 가 severity 등급 역전의 착수 조건으로 **"THERMAL 축 사람 라벨 6건"** 을
걸고 `[대기]` 로 표시하고 있었다. 계획서가 정한 순서대로 **`6` 의 근거부터 확인**했다 —
그 답에 따라 아래가 갈리고, 가장 싸기 때문이다.

### 1. `6` 은 임의값이 아니었다

`tools/readiness.py:83-87` 에 근거가 그대로 있었다:

> 사용자 답이 등급과 무관하다면(귀무가설) 한 방향으로 몰릴 확률은 3건에서 12.5% 로
> 우연히도 나오지만 6건이면 1.6% 다.

이항검정이다. 계획서의 분기대로라면 **"표본을 채우는 방향이 맞다"** 가 된다.

### 2. 그런데 채울 기계가 없다

채우려면 THERMAL 사건이 나야 한다. 관측 중인 두 기계를 다 봤다.

```
이 PC    문턱 97.0도(load_median + 5) > 부하 시 최고 94.0도   -> 구조적 발화 불가 (08-19 실측)
노트북   GPU 컬럼 NULL 238/238 · machine_profile 에 gpu 키 없음 -> NVIDIA GPU 가 없다
```

노트북은 온도 분포를 비교할 것도 없었다. **수집기가 pynvml 을 쓰므로 GPU 축이 통째로
비어 있다** — 스냅샷 3개(08-17/18/19, 고유 475분 버킷)에서 `gpu_util`·`gpu_temp`·
`gpu_vram` 이 전부 NULL 이고 `gpu_util_max` 의 최대값이 `None` 이다.

**미리 적어 둔 의심 신호가 여기서 걸렸다** — *"GPU 표본 수가 0 이면 재고 있는 것은
온도 분포가 아니라 NVML 수집 여부다."* 그 한 줄이 없었으면 "노트북도 온도가 낮다"는
엉뚱한 결론을 적을 뻔했다. 08-17 의 "재는 축이 틀렸다"와 같은 자리다.

**계획서가 예상한 세 분기 중 어느 것도 아니었다.** 근거는 통계적으로 타당하고(→ 조건을
내리는 것은 답이 아니다), 축을 바꿀 수도 없고(CPU 라벨 7/7 이 `normal` 이라 미탐 방향에
답하지 못한다), 그렇다고 조건이 틀린 것도 아니다. **틀린 것은 조건이 아니라, 조건이
`[대기]` 로 보인다는 사실이었다.**

### 3. 고친 것 — 조건이 "충족될 수 있는가"를 같이 잰다

`[대기]`(부족하다, 더 모으면 찬다)와 `[막힘]`(모을 곳이 없다)은 다른 상태인데, 건수만
세면 둘이 똑같이 보인다. 2026-07-29 Phase 6 과 이 건이 정확히 같은 함정이었다.

- `Check.stalled` — 그 조건의 표본 공급이 멈췄으면 이유를 담는다.
- `_axis_supply_stall()` — **라벨이 아니라 사건을 센다.** 라벨은 사람이 눌러야 생기므로
  "안 눌렀다"와 "생기지 않았다"가 섞인다. 조건이 막혔는지를 가르는 것은 *물어볼 사건이
  오는가* 다.
- `SUPPLY_STALL_DAYS = 7` — 마지막 사건 이후 **관측된 날**을 센다(달력이 아니다).
  PC 를 안 켠 날까지 세면 여행 다녀온 것이 조건 재설계 신호가 된다.
- 출력 맨 끝에 `막힌 조건:` 줄을 따로 낸다. 목록 안에만 있으면 "아직 대기 중"으로 읽힌다.

**배선을 양방향으로 확인했다** (기본값이 아닌 값으로 — 전역 규칙 3):

```
stall=30 -> 대기    stall=7 -> 막힘     축=CPU -> 대기
```

임계도 축도 판정을 실제로 움직인다. 축을 CPU 로 바꿨을 때 `[대기]` 로 돌아오는 것이
중요하다 — 그게 아니면 축이 아니라 달력을 재고 있는 것이다.

### 남은 판단 (데이터가 답할 수 없다)

**severity 등급 역전은 폐기가 아니라 하드웨어 대기다.** 조건도 근거도 유효하고, GPU 가
있고 발열이 실제로 나는 기계가 오면 그날 다시 유효해진다. 그래서 `readiness` 에서 빼지
않고 `[막힘]` 으로 남겼다 — 빼면 다음 세션이 계획서 원문을 보고 같은 조건을 다시 세운다.

### 덤 — 계획서의 전제 하나가 틀렸다

> "스냅샷에 `machine_profile` 테이블이 안 들어와 판단할 수 없었다"

**들어와 있었다.** 테이블이 아니라 `export_meta` 의 키다. 그리고 그 안에 답이 있었다:

```
freq_max_mhz 1300.0 · single_thread_mops 3.675 · seq_write_mbps 198.1 · total_gb 15.69
```

**노트북은 아직 부하 중에 잰 프로파일로 돌고 있다.** 확인 못 한 것이 아니라 확인할
자리를 잘못 본 것이었다.
