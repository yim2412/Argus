# 신호가 0인 실패

> 예외도, 로그도, 붉은 테스트도 없이 죽는 것들. 상주 프로그램은 **죽었다는 사실조차
> 아무 데도 도달하지 않는다.** 다섯 번 겪었고, 그중 하나는 발견이 순전히 운이었다.
>
> 2026-07-30 ~ 2026-08-15 · 근거 커밋은 맨 아래

## 이 프로그램의 조건

Argus 는 Windows 상주 프로그램이다. `pythonw.exe` 로 돌아서 **콘솔이 없고, 따라서
stderr 가 갈 곳이 없다.** 사용자에게 말하는 경로는 트레이 아이콘과 풍선 알림뿐이다.

이 조건이 만드는 실패 모양은 크래시가 아니다. **아무 일도 일어나지 않는 것**이다.
그리고 설계 규칙 4 는 이렇게 적혀 있다 — *"조용히 실패하지 않는다."* 아래 다섯 건은
전부 그 규칙을 어긴 자리다.

---

## 1. 스레드가 몇 주 동안 죽어 있었다

지문(fingerprint) 갱신은 6시간 주기로 돈다. `procleak` 이 "이 프로그램은 원래 핸들을
많이 쓴다"를 판단하는 근거라, 낡으면 억제가 잘못된 기준으로 돈다.

**그게 사실상 "기동 시 1회"로 줄어 있었다.**

```
AttributeError: 'FingerprintBuilder' object has no attribute 'throttleable'
```

`FingerprintBuilder` 가 `Component` 를 상속하지 않고 덕 타이핑으로 `name`·`interval_s`·
`tick` 만 갖췄다. 그런데 수퍼바이저는 매 틱 `throttleable` 도 읽고, **그 참조는 `tick()`
을 감싼 `try` 바깥**이었다. 결과적으로 이 컴포넌트는 **첫 틱 직후 항상 죽었다.**

### 어떻게 알아냈나 — 운이었다

**exe 빌드가 콘솔을 띄운 덕에 드러났다.** Phase 14(패키징)에서 처음 exe 를 만들었고,
그 빌드가 콘솔 창을 띄웠고, 거기에 traceback 이 찍혔다. 상주는 `pythonw` 라 stderr 가
없고 파이썬의 스레드 사망은 기본적으로 stderr 로만 알려진다 — **그 경로가 통째로
막혀 있었다.**

패키징을 안 했으면 아직도 몰랐을 것이다. 실질 피해가 작았던 것도 운이다 — 이 PC 는
재기동이 잦아 그때마다 한 번씩은 갱신됐다. 며칠 연속 켜 두는 사용자에게는 그 운이
없다.

### 고칠 때 셋으로 나눴다 — 원인, 재발 방지, 그리고 "죽었다는 사실"

1. `FingerprintBuilder(Component)` 로 상속. 전수 조사에서 규약을 어긴 컴포넌트는
   이것 하나뿐이었다.
2. **`Supervisor.add()` 가 등록 시점에 터진다.** 기동 시점의 시끄러운 실패가 런타임의
   조용한 죽음보다 낫다.
3. 컴포넌트 스레드 전체를 감싸 사망을 로그와 크래시 파일에 남긴다.

2번의 **검사 범위를 좁힌 것이 중요하다.**

```python
# argus/runtime/supervisor.py
# 규약 검사는 "없으면 조용히 죽는 것"만 막아야 하고, 과하게 잡으면 …
_REQUIRED = ("name", "interval_s", "tick", "throttleable")
```

`setup`·`teardown` 은 넣지 않았다. 그것들은 `try` 안에서 불리므로 없어도 조용히 죽지
않고, 넣으면 덕 타이핑 테스트 대역까지 거부한다(실제로 그랬다). **검사의 기준은
「규약에 있는가」가 아니라 「없을 때 조용히 죽는가」다.**

## 2. 자식 프로세스의 실패 원인이 통째로 사라졌다

웜 내보내기는 자식 프로세스로 돈다(`argus --export-warm`). 자식이 실패하면 부모가
그 stderr 를 로그에 남긴다 — 그렇게 되어 있었다.

문제는 이 코드였다.

```python
done = subprocess.run(..., capture_output=True, text=True)   # encoding 없음
...
log.warning("웜 내보내기 자식이 실패했다", extra={"stderr": (done.stderr or "")})
```

`text=True` 만 쓰면 **실행 PC 의 ANSI 코드페이지**로 디코딩한다. 그런데 자식은
우리 자신이고, `logging_setup.setup()` 이 stdout/stderr 를 **UTF-8 로 reconfigure**
한 상태로 쓴다(한글 로그 때문이다). 두 인코딩이 어긋난다.

**그 어긋남이 조용해서 위험하다.**

- 디코딩은 `subprocess` 의 **reader 스레드 안**에서 일어난다 → 예외가 부모까지 안 온다
- `run()` 은 **정상 반환**하고 **깨진 스트림만 `None`** 이 된다
- `(done.stderr or "")` 가 그 `None` 을 빈 문자열로 바꾼다
- **자식이 왜 실패했는지가 통째로 사라진다**

예외도 백오프도 재시도도 없다. **신호가 0이다.** 스레드 traceback 은 상주의 진짜
stderr 로 새는데, `pythonw` 라 아무 데도 안 남는다(위 1번과 같은 구멍).

방어 코드가 증거를 지운 것이다. `(x or "")` 는 "값이 없어도 안 죽게" 하려고 쓰는
관용구인데, 여기서는 **"실패 원인이 없어도 안 죽게"** 가 됐다.

### 캘리브레이션은 더 나쁘다

같은 자리가 하나 더 있었다. `machine/calibration.py` 가 PowerShell 로 디스크 매체를
조회하는데, **PowerShell 오류 메시지는 실행 PC 언어로 나온다.** 그때 `stdout` 이
`None` 이 되면 `(result.stdout or "")` 가 조용히 `"unknown"` 으로 떨어진다.

**HDD/SSD 판정이 틀린 채로 `machine_profile` 이 굳는다.** 이 프로젝트는 모든 임계값을
그 프로파일 기준으로 상대화하므로, 첫 실행에서 조용히 틀린 값이 굳으면 그 PC 의 탐지
전체가 그 위에 선다.

### 이 PC 에서는 재현되지 않는다

개발 PC 는 2026-08-15 부터 UTF-8 시스템 로캘(ACP 65001)이다. **배포 대상은 CP949 다.**
즉 이 버그는 실행만으로는 절대 안 드러난다.

그래서 회귀 테스트를 둘로 나눴다.

| 테스트 | 무엇을 |
|---|---|
| 배선 | `subprocess.run` 에 넘긴 인자를 직접 본다 (`encoding` 이 있는가) |
| 피해 재현 | `cp949` 로 읽으면 `stderr` 가 **`None` 이 된다**는 것을 재현한다 |

**뒤엣것이 없으면 "왜 그 인자가 필요한가"가 남지 않는다.** 그리고 소스에도 재현
방법을 한 줄 남겼다.

```python
# argus/storage/warm.py:449
# 재현: `encoding="cp949"` 로 바꿔 돌리면 stderr 가 `None` 이 된다.
encoding="utf-8",
```

> **곁가지 하나.** 이 수정의 무력화 테스트를 처음 등록할 때 `pass` 를 함수 인자 자리에
> 넣어 `SyntaxError` 가 났고, 그게 "잡힘"으로 집계됐다. **테스트는 실행조차 안 됐다.**
> 무력화는 **돌아가는 코드**여야 측정이 성립한다.

## 3. 화면만 조용히 비었다

타임라인 화면이 이틀 넘은 날짜를 통째로 못 그리고 있었다. 데이터는 멀쩡히 있었다.

원인은 `read_parquet` 에 `union_by_name` 이 없던 것이다. 08-03 에 `gpu_clock_sm_*`
컬럼을 추가한 뒤로, **그 컬럼이 없는 07-27~08-02 파티션과 합쳐 읽으면 `Binder Error`**
가 났다.

그 예외가 UI 안에서 삼켜져 **화면만 비었다.** 데이터가 없는 날과 조회가 터진 날이
사용자에게 똑같이 보인다.

### 적어 두는 것으로는 안 됐다

이게 이 건의 핵심이다. `PLAN.md` 에 **미리 적혀 있었다.**

> 기존 파티션에는 이 두 컬럼이 없다. 이름 기준 병합이 필요하다.

적어 두고도 못 잡았다. 컬럼을 추가하는 커밋과 그 문장을 읽는 시점이 달랐고, 그
사이에 아무것도 실패하지 않았기 때문이다.

**고침은 코드 한 인자와 테스트 하나였다** — 스키마가 다른 파티션 둘을 만들어 합쳐
읽는 회귀 테스트. 지금은 그 이유가 소스에 붙어 있다.

```python
# argus/storage/warm.py:176
# **`union_by_name` 이 없으면 스키마가 바뀐 날 과거가 통째로 사라진다.**
```

## 4. 수집기가 한 시간 죽어 있었다 — 3,845번 조용히

```
07-29 03:58~05:02   access violation 3,845번 연속   그 구간 gpu_metrics 0행
```

재기동으로만 복구됐다. 원인 둘 다 한 파일에 있었다.

- **`nvmlInit()` 이 `setup()` 에서 한 번뿐이라 드라이버 재시작 시 복구 경로가 없다.**
  남의 PC 에서 GPU 드라이버 업데이트는 흔하고, 그때부터 GPU 모니터링이 영영 죽는다.
- **실패가 `log.debug` 였다.** WARNING 도, 화면 노출도 없었다.

주석은 *"다음 틱에 회복될 수 있으므로 이번만 건너뛴다"* 였다. **그 전제가 틀렸다** —
3,845번 연속으로 회복되지 않았다. 한 번의 실패를 무시하는 것과 1시간의 실패를
무시하는 것은 다른 일인데, 코드는 그 둘을 구분하지 않았다.

이건 설계 규칙 4 의 정면 위반이다. 사용자는 "GPU 수집이 지금 실패 중"을 볼 방법이
없었고, 로그조차 기본 레벨에서 안 보였다.

> **아직 안 고친 것이 남아 있다.** 각 수집기의 `describe()` 가 건강 상태를 들고 있지만
> **그 값을 읽는 것은 단독 스모크뿐이고 화면으로 가지 않는다.** WARNING 과 복구 시도는
> 생겼지만, 규칙 4 의 "드러내 놓고"를 완전히 만족하려면 그 경로가 필요하다.

## 5. 어떻게 죽었는지가 남지 않았다

```
system_events:   startup 17건 · shutdown 3건
```

**14건은 아무 흔적도 없다.** `shutdown` 은 시그널 핸들러를 거친 정상 종료에서만
기록되는데, 상주 프로그램이 실제로 죽는 방식은 대부분 그게 아니다 — Windows 종료,
전원 차단, 강제 종료, 크래시.

남의 PC 에서 *"어제 밤부터 안 돌았다"* 는 제보를 받았을 때, 사용자가 껐는지 재부팅
됐는지 크래시인지 구분할 근거가 없으면 **진단이 성립하지 않는다.**

고침은 다음 기동 시점에 **직전 세션을 역추적**하는 것이다. 마지막 `startup` 뒤에
종결 이벤트가 없으면 미종결로 보고, 마지막 데이터 행의 시각을 사망 시각으로 추정한다.
부팅 시각과 비교해 원인을 가른다.

| 판정 | 뜻 |
|---|---|
| `reboot_or_power_loss` | 부팅이 사망보다 뒤 |
| `process_killed_or_crash` | 같은 부팅 세션 안에서 프로세스만 죽었다 — 크래시를 의심할 쪽 |
| `unknown` | `psutil` 을 못 쓰면 **단정하지 않는다** |

이벤트의 `ts` 는 '지금'이 아니라 **사망 추정 시각**이다. 그래야 시간순 정렬이 유지되고
관측 공백 구간의 시작점을 그대로 읽을 수 있다.

> **Windows 에는 깨끗하게 끄는 방법도 없었다.** SIGTERM 이 없고, `pythonw` 에는 Ctrl
> 이벤트가 안 닿고, 창이 없으니 `taskkill` 의 WM_CLOSE 도 무의미하다. `--stop` 을
> 붙이기 전까지 **정상 종료 경로가 아예 존재하지 않았다.**

## 그래서 무엇을 바꿨나

다섯 건의 공통점은 "버그가 어렵다"가 아니다. **다섯 건 전부 원인 자체는 한 줄짜리였다.**
어려웠던 것은 *그게 일어나고 있다는 사실이 어디에도 없었다*는 것이다.

되풀이해 나온 것 넷을 규칙으로 남겼다.

| | |
|---|---|
| **방어 코드가 증거를 지우지 않는지 본다** | `(x or "")`·`except: pass`·`log.debug` 는 실패를 없애는 게 아니라 **안 보이게** 한다 |
| **`capture_output=True` 를 볼 때마다 `encoding=` 이 있는지 확인한다** | 없으면 실행 PC 로캘에 맡기는 것이고, 그 실패는 예외가 아니라 `None` 으로 온다 |
| **시끄러운 실패가 조용한 죽음보다 낫다** | 규약 검사는 등록 시점에 터뜨린다. 단, **"없을 때 조용히 죽는 것"만** 검사한다 |
| **죽더라도 죽었다는 것은 알아야 한다** | 스레드 사망을 로그와 크래시 파일에. 상주는 stderr 가 없다 |

그리고 이 다섯 건이 **전부 다른 계층**에서 나왔다는 것이 남는다 — 스레드 수퍼바이저,
자식 프로세스, 스토리지 조회, 수집기, 프로세스 생명주기. 한 군데를 고쳐서 될 종류가
아니었고, 그래서 규칙으로 옮겼다.
