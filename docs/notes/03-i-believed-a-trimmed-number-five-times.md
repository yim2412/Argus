# 트림된 값을 다섯 번 믿었다

> Windows 가 워킹셋을 트림한다는 사실 **하나**가, 석 달 동안 **서로 다른 다섯 개의
> 판정**을 차례로 망가뜨렸다. 1회차에서 이미 정체를 알아내 계측을 붙이고 회귀
> 테스트까지 고정했는데, 그 뒤로 네 번 더 걸렸다.
>
> 2026-07-27 ~ 2026-08-19 · 근거 커밋은 맨 아래

## 트림이 무엇인가

Windows 는 프로세스가 유휴 상태이거나 다른 프로세스에 메모리 압박이 있으면, 그
프로세스의 **워킹셋**(물리 메모리에 올라와 있는 페이지)을 줄인다. 페이지는 디스크로
내려가고, 다시 쓰이면 **소프트 페이지 폴트**로 되돌아온다.

이때 `RSS`(=워킹셋)는 줄어든다. **커밋된 메모리(`private`)는 그대로다.**

즉 RSS 는 "이 프로그램이 얼마나 메모리를 쓰는가"를 재지 않는다. **"OS 가 지금 이
프로그램에게 물리 메모리를 얼마나 내주고 있는가"** 를 잰다. 그 둘은 다른 질문이고,
Argus 는 그 차이에 다섯 번 걸렸다.

## 1회차 (07-27) — "RSS 가 내려가니 누수는 없다"

Phase 1(수집 레이어)의 마지막 미완 항목이 "RSS 장기 추세"였다. 6시간 소크를 돌리고
10분 버킷으로 집계했다.

```
+400m  63.7MB   +410m  29.4MB   +440m  27.2MB   +470m  18.8MB   +480m  17.9MB
```

**내려가고 있다.** 누수라면 올라가야 하니 없다고 읽으면 된다.

그게 아니었다. 백그라운드(`pythonw`)로 도는 프로세스의 워킹셋을 Windows 가 트림한
결과였다. **누수가 실제로 있어도 트림이 그걸 가린다.**

당시 기록에 이렇게 적혀 있다.

> 이대로 6시간을 채우고 "RSS 안정, 누수 없음"으로 Phase 1 을 닫았다면, **측정하지
> 않은 것을 측정했다고 적는 셈**이 된다.

### 여기서 제대로 했다

가설로 두지 않고 **트림을 인위로 일으켜** 확정했다. `SetProcessWorkingSetSize(-1, -1)`
는 Windows 가 유휴 백그라운드 프로세스에 하는 일을 즉시 재현한다. 64MB 를 실제로
건드린 뒤 트림했다.

| | RSS | private | peak_wset | page_faults |
|---|---|---|---|---|
| 트림 전 | 95.8MB | 85.4MB | 95.8MB | 24,709 |
| 트림 후 | **1.0MB** | **85.4MB** | 95.9MB | 24,979 |

RSS 는 95.8 → 1.0MB 로 무너지고 private 은 85.4MB 그대로다. 소크에서 본 하강 곡선의
정체가 이것이었다.

그리고 셋을 다 했다 — **계측을 붙이고**(`private_mb`·`peak_wset_mb`·`page_faults` 세
컬럼), **회귀 테스트로 고정하고**, **판정 지표를 정했다.**

> **예산 판정은 계속 RSS 로 한다.** 바꾸고 싶은 유혹이 있지만 바꾸지 않았다. 예산
> "RSS 300MB"는 *지금 물리 메모리를 얼마나 붙들고 있는가* 라는 뜻이고, 트림된 뒤
> 줄어든 값이 그 질문에는 맞는 답이다. **지표마다 답하는 질문이 다르다 — 예산은
> RSS, 누수는 private.**

`USS` 도 후보였지만 뺐다. 워킹셋 기반이라 **같은 문제를 그대로 겪고**, Windows 에서
계산 비용이 가장 크다(전 페이지 스캔). 관측자는 가벼워야 한다.

**이 판단은 지금 봐도 옳다.** 그런데 3주 뒤에 물린다.

## 2회차 (08-04) — "평탄하다"를 "정상이다"로 읽었다

예산 초과가 반복돼 원인을 쫓던 중이었다. `PLAN.md` 에 진단이 이렇게 적혀 있었다.

> RSS 순간값만 튄다 · `private_mb` 는 501MB 로 평탄

**평탄한 505MB 자체가 예산(300MB)의 1.7배였다.**

"평탄하다"는 *변화가 없다* 는 뜻이지 *정상이다* 라는 뜻이 아니다. 누수를 찾느라
기울기만 보고 있어서, 절편이 이미 두 배 가까이 높다는 것을 지나쳤다. 원인 추적이
하루 늦었다.

원인은 결국 **DuckDB 파라미터 바인딩** 하나였다. 값을 바인딩하면 `read_parquet` 의
필터 푸시다운을 못 해 Parquet 을 통째로 메모리에 올린다.

```
지문 빌드의 웜 조회   바인딩:  private +416MB · 0.36초
                     리터럴:  private + 18MB · 0.06초    ← 결과는 1,396칸 전부 동일
```

메모리 **23배**, 속도 **6배** 차이가 값의 표현 방식 하나에서 났다.

### 진단이 네 번 뒤집혔고, 매번 측정이 죽였다

| 가설 | 어떻게 죽었나 |
|---|---|
| "RSS 순간값만 튄다" | 700MB 가 2분 지속. 순간이 아니었다 |
| `self_telemetry.active` 로 잡는다 | throttle>0 표본의 **99.7%가 None** — tick 이 5초 표본보다 짧다 |
| DuckDB 버퍼 풀 | `memory_limit` 을 128MB 로 걸어도 +442MB |
| `COUNT(DISTINCT)` | 무죄. 세 방식 모두 +15~17MB, 결과도 동일 |

좁힌 방법은 **조건 수를 계단으로 늘려 본 것**이다. `exclude` 구간을 0·5·10·20·30·43
으로 늘려 재자 **0→5 에서 계단처럼 뛰고 그 뒤로 평평**했다. "조건이 많아서"가 아니라
**"params 가 있느냐 없느냐"** 였고, 거기서 원인이 나왔다.

## 3회차 (08-12) — 계단을 경사로 봤다

자기계측 7일치(72,956표본)를 보고 자기 메모리 누수를 의심했다. 이어 붙여 보면 우상향
곡선이다.

**세션 경계(`system_events` 의 `startup`)로 가르니 답이 바로 나왔다.**

```
세션 20개 — private 은 매번 52~53MB 에서 시작한다 (세션 간 누적 없음)
끝값이 두 갈래:   100~135MB (스레드 35)  |  520~550MB (스레드 46~47)
```

이봉분포이고, **+420MB 와 +11~35 스레드가 함께 온다.** 한 세션을 펼치면 경사가 아니라
**계단**이다 — 08-06 05:43 **한 걸음에 +420.4MB**(전체 증가의 89%), 스레드 14 → 49,
그리고 그 뒤 2.2시간은 사실상 평평했다.

정체는 임포트 비용이었다.

```
import pyarrow           private +366.0MB   스레드 +11
import duckdb            private   +7.0MB   스레드 +11
```

`warm.export_date()` **안에서** `import pyarrow` 를 하므로(하루 한 번), 그 세션은
영구히 +366MB 를 안고 간다. **파이썬은 모듈을 프로세스 수명 동안 붙들고 있으므로
함수 안 임포트도 일회성 상주 비용이 된다.**

### 여기서 남긴 문장이 나중에 다시 쓰인다

> **"며칠 더 관찰"이 필요하지 않았다** — 필요한 것은 세션 경계로 가르는 것뿐이었다.
> 이어 붙이면 계단이 경사로 보이고, 그러면 **없는 누수를 쫓게 된다.**

고침은 `import pyarrow` 를 자식 프로세스로 떼는 것이었고(자식이 죽으면 366MB 도
사라진다), `private 535MB → 208MB` 로 예산 아래에 들어왔다.

## 4회차 (08-16) — 메모리와 아무 상관없는 자리

여기서 성격이 바뀐다.

개발 중에 창(PySide6)을 띄우고 **"창이 떴는가"를 판정**해야 했다. 프로세스의 RSS 를
보고 판정했다 — 창을 그리면 메모리를 쓸 테니까.

**RSS 5.6MB 일 때도 창은 떠 있었다. 이걸로 세 번 오판했다.**

게임처럼 메모리를 많이 쓰는 프로세스가 있으면 Windows 가 **다른 프로세스의 워킹셋을
트림한다.** 창은 멀쩡히 떠 있는데 RSS 만 무너져 있었다.

판정을 `EnumWindows` + `IsWindowVisible` 로 바꿨다. `Get-Process` 의
`MainWindowTitle`·`MainWindowHandle` 도 **창이 떠 있는데 비어 있었다.**

> **이 회차가 이 노트에서 제일 중요하다.** 앞의 셋은 전부 "메모리를 재는 일"이었다.
> 07-27 에 배운 것을 메모리 판정에는 적용하고 있었는데, **창이 떴는지를 재는 자리에는
> 옮겨가지 않았다.** 한 번 배운 교훈은 그 교훈이 처음 나온 영역 안에 머무른다.

## 5회차 (08-19) — 예산이 Argus 가 아니라 OS 를 재고 있었다

상태 확인 중에 상주가 **스로틀 3 에 25분째 걸려 있는 것**을 봤다. CPU 는 예산의
1/40(0.05~0.5% vs 2%)인데 RSS 하나로 최대 단계까지 늦춰져 있었다.

**답은 한 표에 다 있었다 — 20분을 5초 간격으로 펼치니.**

```
시각      RSS      private   peak_wset   page_faults
23:50    84.3      184.8      325.2      4,378,923
23:56   180.2      184.8      325.2      4,439,088   faults +28,771
23:59   247.7      184.8      325.2      4,461,020
00:03   309.7      184.8      325.2      4,491,896   <- 스로틀 3
00:11   301.3      184.8      325.2      4,502,763
```

**`private_mb` 와 `peak_wset_mb` 가 20분 내내 소수점까지 상수다.** 늘어난 것은 RSS
하나뿐이고, 늘어난 방식은 새 할당이 아니라 **소프트 페이지 폴트** — 이미 커밋된
페이지가 워킹셋으로 되돌아온 것이다.

낮 시간대를 보면 더 분명하다. **RSS(73~90MB) < private(156~184MB)** 인 상태가 이
세션 표본의 **91.8%** 다. 워킹셋이 커밋된 메모리보다 작다는 것은 OS 가 트림해 뒀다는
뜻이다.

> **즉 낮의 84MB 가 가짜고 밤의 310MB 가 실제 크기다.** 트림이 그것을 가리고 있었을
> 뿐이다. **예산 판정은 Argus 의 행동이 아니라 OS 의 트림 여부를 재고 있었다.**
> Argus 가 아무것도 더 하지 않아도 스로틀이 걸린다.

### 그리고 스로틀이 막아낸 사고는 0건이었다

```
throttle  lv0 98.62%  lv1 0.51%  lv2 0.14%  lv3 0.73%    (스로틀 합계 81분)
drop_count 최대 0       큐 깊이 최대 1,346 / 20,000 (6.7%)
CPU > 2%   0.57%        RSS > 300MB  0.71%
peak_wset 실측 최대 325MB   <- 예산보다 크다
```

반대로 스로틀 3 은 수집 주기를 ×10 으로 늘려 **관측 해상도를 1/10 로 떨어뜨린다.**
손실이 작았던 것은 그것이 주로 밤 유휴 시간에 걸렸기 때문이지 설계가 그래서가 아니다.

## 07-27 의 결정이 어떻게 물렸나

5회차의 결론은 *예산 판정이 OS 를 재고 있다* 는 것이다. 그런데 **"예산은 RSS"는
07-27 에 근거를 적어 가며 의도적으로 정한 것**이었다.

그 결정이 틀렸던 게 아니다. **조건이 바뀐 것을 아무도 다시 묻지 않았다.**

> 300MB 는 **기능이 적고 DB 가 작던 시절에 정해진 값**이고, 그 뒤 Phase 4-B·6 이
> 붙으면서 베이스라인이 300MB 쪽으로 자랐다.

즉 07-27 의 *"예산에는 트림된 값이 맞는 답"* 은 **여유가 충분할 때만 참이었다.**
베이스라인이 문턱에 붙으면 같은 지표가 "얼마나 쓰는가"가 아니라 "OS 가 지금 트림
중인가"를 재게 된다. 그 전환점이 어디였는지는 아무도 안 봤다.

### 기각한 대안 둘 — 둘 다 이미 문서에 답이 있었다

코드를 읽기 전에 제안 둘을 내놓았다. **둘 다 이미 기각돼 있었다.**

- **판정을 `private_mb` 로 바꾼다** — `CHANGELOG.md` 에 기각돼 있다(위 07-27 인용).
  실무적으로도 틀린다: private 로 재면 **08-12 의 RSS 745MB 워킹셋 폭주를 못 잡는다**
  (그때 private 은 536MB 였다).
- **히스테리시스를 넣는다** — 이미 있다(`breach_streak_to_throttle: 3` /
  `calm_streak_to_relax: 12`). 관측된 3↔2 진동은 고장이 아니라 설계대로 도는 것이다.

**같은 자리를 다시 건드릴 때 기록을 먼저 읽으라는 규칙이 정확히 이 경우를 말한다.**
그 기록이 없었으면 07-27 에 한 번 기각한 방향으로 되돌아갔을 것이다.

### 그래서 바꾼 것은 값이 아니라 재는 대상이다

예산을 350 으로 올리는 안은 **실측이 부정했다**(`private` 최대 355.6MB ·
`peak_wset` 최대 461.5MB — 올리자마자 넘는다). *자라는 값을 뒤쫓는 일*이 된다.

대신 RSS 경고선이 **실제 압박이 동반될 때만** 스로틀하도록 바꿨다. 압박과 무관한
폭주는 별도의 하드 상한이 잡는다.

```yaml
# argus/config/defaults.yaml
  rss_mb: 300          # 압박(큐 적체·표본 유실)이 동반될 때만 스로틀
  rss_hard_mb: 600     # 압박과 무관한 폭주는 여기서 잡는다
  pressure_queue_ratio: 0.5
```

그리고 이 판단의 근거를 지금 소스가 들고 있다.

```python
# argus/runtime/budget.py:19
원인은 RSS 가 Argus 의 행동이 아니라 **OS 의 워킹셋 트림**을 재기 때문이다.
```

> ⚠️ **`pressure_queue_ratio: 0.5` 에는 실측 근거가 없다.** 두 기계 어디에서도 큐가
> 15% 를 넘은 적이 없어 분포에 문턱을 그을 자리가 없었다. 압박이 한 번도 일어나지
> 않았기 때문이지 이 값이 검증돼서가 아니다 — **첫 압박 관측이 곧 이 값을 다시
> 정할 근거다.**

## 곁가지 — "drop 0 이니 안전하다"가 순환일 뻔했다

완화의 근거를 *"스로틀 81분 동안 `drop_count` 0"* 으로 삼으려다 멈췄다.

**스로틀이 걸려서 0 일 수도 있다.** 수집 주기가 ×10 이면 큐 유입이 줄어 당연히 안
버린다. 보호 장치가 켜진 구간에서 그 장치의 필요성을 재고 있었던 것이다.

**대조군은 이미 데이터 안에 있었다 — `lv0` 구간이다.**

```
        lv0 표본     큐 최대                구간 drop
이 PC    67,140     2,402/20,000 (12.0%)        0
노트북  118,032       964/20,000 ( 4.8%)        0
스로틀이 걸린 lv1~3 은 오히려 큐가 더 낮다
```

정상 주기로 풀가동한 구간에서도 12% 를 안 넘었다. **막아준 것이 아니라 막을 것이
없었다.** 이 확인 없이 완화했으면 근거 없는 변경이 됐다.

## 곁가지 둘 — 두 기계가 갈린 게 아니었다

08-19 에 이 PC 와 노트북의 `private` 평균이 169 vs 69MB 로 갈리는 것을 보고 *"이 PC 가
더 무거운 Argus 를 돌리기 때문"* 이라고 읽었다.

**곡선 위의 다른 점을 비교한 것이었다.** 세션 경계로 가르니 이 PC 는 **19개 세션이
전부 52~54MB 에서 시작**했다. 이 PC 는 하루에도 여러 번 재시작돼(7일에 19세션) 리셋이
자주 걸렸고, 노트북은 117시간 연속 가동이라 단조 곡선이 그대로 보였을 뿐이다.

08-19 에 적어 둔 예측이 그대로 맞았다.

> 노트북은 안 걸리는 것이 아니라 **아직 안 걸린 것이다** — 다만 이것은 예측이지
> 실측이 아니다.

노트북도 이제 스로틀 3 에 167회 걸렸고 RSS 최대 310.3MB 다. **예측을 예측이라고
적어 둔 덕에, 나중에 그것이 맞았다는 것을 말할 수 있게 됐다.**

## 무엇이 남았나

**지표가 답하는 질문을 적어 두는 것으로는 부족했다.** 07-27 에 *"예산은 RSS, 누수는
private"* 을 정확히 적었고 그 문장은 계속 옳았는데, 그 문장이 **언제까지 옳은지**는
적혀 있지 않았다.

지금 다시 쓴다면 이렇게 적을 것이다.

| 적었던 것 | 빠졌던 것 |
|---|---|
| 예산은 RSS 로 잰다 | **베이스라인이 예산의 절반을 넘으면 이 선택을 다시 본다** |
| 누수는 private 으로 잰다 | (이건 그대로 유효했다) |

그리고 4회차(창 판정)가 말하는 것 — **교훈은 그것이 나온 영역 밖으로 자동으로
옮겨가지 않는다.** 메모리를 잴 때는 트림을 조심했는데, 창이 떴는지 잴 때는 같은
사람이 같은 함정에 다시 빠졌다. 규칙을 "메모리 계측 절"이 아니라 **"RSS 로 무언가를
판정하려 할 때마다"** 로 적었어야 했다.

**아직 안 풀린 것도 있다.** 08-31 에 큐가 23.8% 까지 찬 것을 압박으로 읽을 뻔했는데,
실제로는 **단일 행 하나의 쓰기가 115초** 걸린 것이었다(5초 주기가 111초 통째로 멎었고,
정체가 풀리자 20초 만에 큐가 빠졌다). 스로틀은 막힌 쓰기를 못 뚫고 오히려 정체 구간의
증거를 지운다. **락 블록 안의 무엇이 10~39초인지는 아직 모른다.**
