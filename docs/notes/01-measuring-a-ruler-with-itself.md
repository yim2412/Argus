# 자를 자로 쟀다

> 탐지 문턱을 정하려고 만든 시험 도형이, **그 문턱을 품고 태어난 것**이었다.
> 그걸 찾아낸 것은 결과를 보기 전에 적어 둔 의심 신호 한 줄이다.
>
> 2026-08-17 · 근거 커밋은 맨 아래

## 무엇을 정하려던 참이었나

Argus 는 프로세스 메모리 누수를 `procleak` 이라는 탐지기로 잡는다. 판정 조건은 셋이다.

```
증가량   delta >= min_delta        (이 PC 1,303.6MB)
배수     last/first >= 3.0
단조성   비감소 표본 비율 >= 0.9   ← 이번에 건드리려던 것
```

세 번째가 `monotonic_ratio` 다. 등락하며 오르는 정상 프로세스 — 캐시가 찼다 비워지는
브라우저 같은 것 — 를 거르려고 있다.

이 값을 낮출지 말지는 작은 문제가 아니었다. `PLAN.md` 가 Phase 5(다차원 이상탐지)와
Phase 7(시퀀스 모델)을 **보류**해 두고 조건을 이렇게 적어 뒀기 때문이다.

> **더 싼 대안이 먼저다.** 되돌림 20~30% 를 잡고 싶다면 `monotonic_ratio` 를 0.9 에서
> 낮추는 것이 모델을 들이는 것보다 압도적으로 싸다(상수 하나 · config 에 이미 있다).
> **Phase 5·7 을 여는 근거로 쓰려면 이 대안이 먼저 실패해야 한다.**

즉 이 실험은 "상수 하나를 튜닝할까"가 아니라 **"모델을 들일 명분이 있는가"** 를 묻는
자리였다. 그래서 판정 기준을 결과 보기 전에 적었다.

## 첫 번째 관측 — 그리고 첫 번째 오독

톱니 모양 램프를 60분 태워 리플레이했다. 톱니는 "오르다 조금 되돌리기"를 반복하는
도형이고, `--saw-drop` 으로 **되돌리는 양**을 조절한다.

```
되돌림 10%   [발화] procleak 그룹축 +23.6분
되돌림 20%   [미탐]
되돌림 30%   [미탐]
되돌림 50%   [미탐]
```

이걸 보고 이렇게 적었다.

> 미탐이 한 점이 아니라 **연속적**이라, `monotonic_ratio = 0.9` 가 **설계대로** 거르고
> 있다는 뜻이다.

그럴듯했다. 문턱이 우연히 한 점에서만 걸리는 게 아니라 넓은 구간에서 일관되게
거른다는 것은 보통 견고함의 증거다.

**틀렸다. 그리고 틀린 방식이 문제였다.**

## 문턱을 절반까지 낮춰도 아무것도 안 변했다

재현 조건을 맞춘 뒤(그 과정에서 세 번 헛짚었다 — 아래 별도 절) `monotonic_ratio` 를
훑었다.

```
monotonic=0.9    [미탐]  -7.91%p
monotonic=0.85   [발화]  procleak:python.exe(rss_mb) — 램프 시작 22.6분 뒤
monotonic=0.8    [발화]  ... 22.6분 뒤
monotonic=0.7    [발화]  ... 22.6분 뒤
monotonic=0.6    [발화]  ... 22.6분 뒤
monotonic=0.5    [발화]  ... 22.6분 뒤
```

0.85 와 0.5 는 6배 가까이 다른 문턱인데 **발화 지점이 22.6분으로 소수점까지 같다.**

문턱을 낮추는 것은 "더 많이 통과시키는" 일이다. 그런데 아무리 낮춰도 결과가 한 톨도
안 변한다면, **재고 있는 대상의 값이 한 점에 몰려 있다**는 뜻이다.

톱니 구현이 그 이유를 그대로 적고 있었다.

```python
# tools/ramp_replay.py
# 주기의 앞 85% 는 순증가, 뒤 15% 에서 되돌린다. 비감소 비율이 대략 0.85 로 떨어져
# 문턱 바로 아래에 놓인다.
SAW_RISE_FRAC = 0.85
```

**이 톱니는 비감소 비율 0.85 를 만들도록 합성된 도형이다.**

문턱을 0.85 아래로 내리면 잡히는 것은 자명하다. 도형이 0.85 를 만들도록 설계돼
있으니까. 그 사실은 `monotonic_ratio` 에 대해 **아무것도 알려주지 않는다.**
자를 자로 잰 것이다.

## 그리고 이것이 첫 관측의 해석을 뒤집는다

여기서 앞의 "미탐이 연속적이다"로 돌아가야 한다.

`--saw-drop` 은 되돌리는 **양(진폭)** 을 바꾼다. 비감소 비율을 정하는 것은 진폭이
아니라 **시간 비율**이고, 그건 `SAW_RISE_FRAC = 0.85` 로 고정돼 있다.

**즉 되돌림 20%·30%·50% 는 비감소 비율이 전부 0.85 로 같았다.**

```
훑은 것        되돌림 20% → 30% → 50%    (진폭)
재려던 것      비감소 비율               (시간 비율 — 안 움직였다)
```

**4점을 훑은 것이 한 점을 네 번 잰 것이었다.** "연속적 미탐"은 견고함의 증거가 아니라
축을 잘못 잡은 결과다. 스윕 결과가 매끄럽게 일관되면 견고하다고 읽고 싶어지는데,
그 매끄러움은 **아무것도 안 변하고 있을 때도** 똑같이 나온다.

## 무엇이 이 정정을 가능하게 했나

0.85 와 0.8 이 같은 지점에서 발화하는 것을 보고도 그냥 지나칠 수 있었다. `0.85` 라는
값 자체는 나쁘지 않아 보인다 — 0.9 에서 조금 내린 정도다. *"0.85 로 낮추면 잡힌다"* 를
결론으로 적었으면 그날 실험은 성공으로 끝났을 것이다.

그러지 않은 이유는 **측정 전에 적어 둔 판정 기준에 이 줄이 있었기** 때문이다.

> **A·B 를 만족하는 값이 0.9 에 너무 붙어 있으면**(예: 0.88) **의심한다.** 톱니 되돌림
> 20% 는 비감소 비율을 크게 떨어뜨리므로, 미세 조정으로 잡힌다면 내가 재는 대상이
> 톱니가 아닐 수 있다.

이 한 줄 덕에 `0.9 → 0.85` 를 **결론이 아니라 경보**로 읽었다.

판정 기준을 먼저 적는 이유는 보통 "나중에 자기합리화하지 않으려고"라고들 한다. 여기서
실제로 한 일은 그게 아니었다. **기준에 「이러면 의심한다」를 같이 적어 둔 것이 성공처럼
보이는 결과를 한 번 더 보게 만들었다.** 실패 조건만 적었으면 이건 못 잡았다.

## 기준을 폐기하고 질문을 바꿨다

측정 전에 적은 채택 조건 A 는 이랬다.

> A. 톱니를 잡는가 — 되돌림 20%·30% 를 **둘 다** 발화

**A 를 폐기했다.** 이 기준은 *톱니가 독립적인 시험 도형이라는 전제* 위에 서 있었는데
그 전제가 틀렸기 때문이다. B(정상 구간 오탐 0건)와 C(발화 주체 확인)는 실측 데이터에
기대는 기준이라 순환이 아니므로 그대로 뒀다.

| 폐기한 질문 | 바꾼 질문 |
|---|---|
| 합성 톱니를 잡으려면 문턱이 얼마여야 하나 | **실제 프로세스의 비감소 비율은 어떻게 분포하고, 문턱 0.9 는 그 분포의 어디에 서 있나** |

바뀐 질문은 합성 도형이 필요 없다. 실측만으로 답할 수 있다.

## 답 — 이 문턱은 거의 아무것도 안 거른다

`procleak.judge()` 와 같은 식·같은 창(`window_s=900`, `min_samples=20`)으로 실제
프로세스의 비감소 비율 분포를 냈다. 창은 `08-16 18:50~20:30`.

```
시계열 417개 · 중앙값 0.963 · 최소 0.294 · 최대 1.000

비감소 >= 0.90 : 259개 (62.1%)   ← 현재 문턱
비감소 >= 0.85 : 297개 (71.2%)   +38
비감소 >= 0.80 : 321개 (77.0%)   +24
비감소 >= 0.70 : 362개 (86.8%)   +41
```

**후보 수는 오탐 수가 아니다.** 늘어난 것 대부분이 `svchost` 류로 RSS 가 0.5~3.6MB라
`min_delta`(1,303.6MB)를 애초에 못 넘는다. 그래서 정상 구간 리플레이로 실제 발화를
셌다 — 4개 창 × 4개 문턱, 16회.

```
                   procleak        배경룰
mono=0.90          0 · 0 · 0 · 0   1 · 0 · 0 · 0     ← 현재 배포값(기준선)
mono=0.85          0 · 0 · 0 · 0   1 · 0 · 0 · 0
mono=0.80          0 · 0 · 0 · 0   1 · 0 · 0 · 0
mono=0.00          0 · 0 · 0 · 1   1 · 0 · 0 · 0     ← 대조군에서만 1건
```

**0.9 에서 0.8 로 낮춰도 발화가 한 건도 안 는다.** 모든 등락을 허용하는 극단값 0.0 까지
가야 1건이 나온다. 세 조건 중 판정을 실제로 가르는 것은 `min_delta` 이고,
`monotonic_ratio` 는 이 PC 에서 **실질적으로 가장 느슨한 조건**이다.

## "0건" 을 결과로 쓸 뻔했다

위 표에는 앞선 판이 있다. 처음 정상 구간 오탐을 12회 재고 **전부 "발화 0건"** 을 얻었다.

실제로는 지정한 창이 원본 보존 기한을 넘겨 **도구가 `[FAIL]` 로 죽어 있었다.**
집계 스크립트가 종료 코드를 안 보고 **"발화 문자열이 없음 = 0건"** 으로 읽은 것이다.

이게 왜 위험한가. 이 실험에서 **"오탐 0건"은 채택 방향의 신호**다. 측정 실패가 정확히
그 모양으로 위장했다. 그대로 믿었으면 *"오탐이 늘지 않으므로 낮춰도 안전하다"* 가
결론이 됐을 것이다.

살린 것은 **대조군**이다. `--monotonic-ratio 0.0` 은 모든 등락을 허용하므로 여기서는
반드시 무언가 발화해야 한다. 거기서 1건이 나왔다.

> **거기서도 0건이었다면** 앞의 12개 0 은 "오탐이 안 늘었다"가 아니라 **"애초에 잡을
> 것이 없는 조건이었다"** 이고, 전량 무효였다.

수정도 함께 적어 둔다 — 종료 코드와 `[FAIL]` 을 함께 보고, 성공한 회차도 **관측 수를
같이 기록**한다. 창이 비었는데 성공으로 끝나는 경우를 눈으로 잡기 위해서다.

## 재현 조건을 찾는 데 세 번 틀렸다

08-17 표를 재현하려는 첫 세 번이 **전부 다른 답**을 냈다. 재현이 안 되는 기준선 위에서
잰 수치는 아무것도 말하지 않으므로, 이 과정 자체가 실험의 전제였다.

| 시도 | 조건 | 결과 | 무엇이 틀렸나 |
|---|---|---|---|
| 1 | 기본(단일 프로세스·선형) | 발화 +9.0분 | **`--spread` 없음.** 단일이면 PID별 축이 문턱을 쉽게 넘어 `monotonic_ratio` 가 쟁점조차 안 된다 |
| 2 | `--spread 8`, 선형 | 발화 +7.5분 | **`--quadratic` 없음.** 선형은 초반부터 빨리 올라 쉽게 잡힌다. t² 가 실주입 모양이다 |
| 3 | `--spread 8 --quadratic`, 창=13:05 | 발화 +28.3분 (**시스템 룰**) | **창이 다르다.** 이 창은 메모리가 평탄해 「메모리 이상 증가」가 문턱을 넘는다 |
| 4 | 위 + 창=08-16 저녁 | **미탐** (-7.91%p) | 재현 성공 |

**첫 진단("개발 활동 오염")도 틀렸다.** 그 시각의 python 프로세스는 평균 1.1개로
깨끗했다. 창을 바꿔 셋을 재보니 셋 다 일관되게 발화해서 오염 가설이 무너졌고,
그때서야 조건 쪽을 의심했다.

그리고 **이것 자체가 결과였다** — 미탐은 창 의존적이다.

```
08-16 18:50~20:30   [미탐] -7.91%p
08-16 17:20~19:00   [미탐] -2.62%p
08-17 04:20~06:00   [미탐] -6.09%p
08-17 13:05~14:45   [발화] +4.10%p   ← 시스템 룰이 잡는다
```

메모리가 평탄한 창에서는 `procleak` 이 손을 떼도 시스템 룰이 잡는다. 사각지대는
시나리오의 성질이 아니라 **그 시각의 메모리 변동성**에 달려 있었다. 08-17 에 적은
"되돌림 20% 이상은 일관되게 미탐"은 **한 창에서의 관측**이었다.

## 결론 — 채택하지 않는다

`monotonic_ratio = 0.9` 를 그대로 둔다.

- 오탐은 안 는다 (0.8 까지 0건)
- **무엇을 더 잡는지는 증명되지 않았다** (톱니가 순환이라 폐기)
- 이 PC 에서 거의 아무것도 안 거르므로 낮춰도 **동작이 사실상 안 변한다**

이득 0 · 비용 불확실인 변경이다.

### 진짜 산출물은 Phase 5·7 쪽에 있다

`PLAN.md` 는 *"Phase 5·7 을 여는 근거로 쓰려면 이 대안이 먼저 실패해야 한다"* 고
적어 뒀다.

**대안은 실패하지 않았다. 애초에 겨눌 과녁이 없었다.**

*"`monotonic_ratio` 가 설계대로 걸러서 사각지대가 생긴다"* 는 관측이 측정 착오였고,
실측은 그 반대를 가리킨다 — 이 조건은 이 PC 에서 거의 아무것도 안 거른다.

> **즉 「`monotonic_ratio` 사각지대」는 실재하지 않는다.** Phase 5·7 을 여는 근거로
> 준비돼 있던 카드 하나가 없어졌고, 보류 사유("이길 상대가 없다")는 오히려 강해졌다.
> 근거가 필요하면 메모리 누수가 아닌 **다른 축**에서 찾아야 한다.

**실패가 유의미한 결과인 실험이었다.** 다만 그 실패는 예상한 모양이 아니었다 — 대안이
지는 것이 아니라, 대안이 이길 상대가 없다는 쪽이었다.


살아남은 이유는 **결함 주입 보호 구간**이다. 주입 라벨 `#66`(18:19~19:13)과
`#67`(20:16~21:16)이 ±900초 여유와 함께 보존에서 제외되어 있었다.

**② 그래서 이 창에는 33분짜리 구멍이 있다.** 두 보호 구간 사이가 지워졌다.

```
19:20~19:30   17,611행
19:30~19:40        0      ← 보호 구간 사이
19:40~19:50        0
19:50~20:00        0
20:00~20:10   19,628행
```

**즉 오늘 잰 것은 100분이 아니라 67분짜리 창이다.** 그런데도 중앙값이 0.963 → 0.964
로 나왔다. 시계열이 417 → 404 로 13개 준 것의 일부가 이 구멍이고, 나머지는 내가
`_Track` 구성을 제품과 완전히 같게 재현하지 않은 탓으로 본다 — **정확히 어느 쪽이
몇 개인지는 가르지 않았다.**

이 절을 적는 이유는 수치를 확인했다는 것보다, **다시 잴 수 있는지를 실제로 확인하기
전에는 못 잰다고 단정하면 안 된다**는 쪽이다. 이 노트를 쓰기 시작할 때 나는 "그
창은 보존 기한으로 사라졌다"고 적어 두었었다. **그건 보존 설정에서 추론한 것이었고,
실제로 열어 보니 남아 있었다.**

## 남은 의문 — 답하지 못했다

미탐이 왜 창마다 갈리는가. 같은 램프가 창에 따라 탐지·미탐을 넘나든다.

```
08-16 18:50~20:30   [미탐] -7.91%p
08-17 13:05~14:45   [발화] +4.10%p   ← 같은 시나리오인데 시스템 룰이 잡는다
```

`monotonic_ratio` 와 무관한 현상이고(발화한 것은 `rules` 였다), 그 시각의 메모리
변동성이 베이스라인 σ 를 통해 문턱을 움직이는 것으로 **보인다.** 확인하지 않았다.
이쪽이 오히려 실재하는 축일 수 있으나 이번 실험의 범위가 아니었다.
